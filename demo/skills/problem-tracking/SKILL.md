# 问题追踪记录

## 概述

开发过程中遇到的每个问题——编译错误、运行异常、通信失败、配置问题、部署问题——都必须记录到 `docs/development_memory.md`。这形成项目的长期知识库，避免重复犯同样的错误。

## 何时使用

**适用场景：**
- 发生编译或链接错误
- 发生运行时异常或崩溃
- 通信失败（CAN、串口、TCP、WebSocket 等）
- 配置加载/保存失败
- 数据存储失败
- 依赖库缺失
- 环境变量问题
- 权限或路径问题
- 设备连接问题
- 任何意外行为被遇到并解决

**不适用：**
- 正常工作的预期行为
- 已经记录过的问题（先查记录）

## 流程

### 第一步：阅读已有记录

在记录新问题之前，先阅读 `docs/development_memory.md`，检查是否已有类似问题的记录。如果有，引用已有条目而不是重复记录。

### 第二步：立即记录

不要等项目结束后凭记忆补写。问题解决后立即记录，趁细节还清楚。

使用 `references/problem-record-template.md` 中的模板：

```markdown
## 问题编号：YYYYMMDD-NN

### 1. 问题现象
[观察到的现象——错误信息、异常表现]

### 2. 发生环境
- 系统版本：
- 项目版本：
- 编译环境：
- 运行设备：
- 相关模块：

### 3. 问题原因
[已确认的问题原因]

### 4. 解决方法
[已验证可行的解决步骤]

### 5. 涉及文件
[涉及的文件路径]

### 6. 后续注意事项
[以后需要注意什么，哪些操作不要再做]
```

### 第三步：解决方案变更时更新条目

如果后来发现了更好的解决方案，更新已有条目而不是创建重复条目。

### 第四步：在后续方案中引用

编写新方案时（使用 `plan-before-code`），始终检查 `docs/development_memory.md` 中的相关历史问题，并在方案的"历史问题参考"章节中注明。

## 常见借口与反驳

| 借口 | 事实 |
|------|------|
| "我回头再记录" | 细节会很快模糊。解决后立即记录。"回头"通常意味着"永远不会"。 |
| "这个错误太小了不值得记" | 小错误已经浪费了你一次时间。没有记录，下次还会浪费——你或队友的时间。 |
| "修复方法很明显，不需要记录" | 现在明显，6 个月后或对新成员来说，上下文早已丢失。 |
| "我是试出来的，不太确定为什么能工作" | 记录什么有效、什么无效。不清楚原因就标注"原因未确认"。部分知识比没有好。 |
| "这是环境特有问题，不会再出现" | 环境特有问题是最难调试的。这些恰恰是最需要记录的。 |

## 危险信号

- 同一错误多次出现却没有记录
- Agent 推迟到"项目完成后再记录"
- 问题条目缺少原因或解决方法
- 写方案时没有先查阅 `development_memory.md`
- 同一问题有重复条目

## 验证

记录问题后：

- [ ] 问题编号遵循 `YYYYMMDD-NN` 格式
- [ ] 6 个章节全部填写（现象、环境、原因、解决方法、涉及文件、注意事项）
- [ ] 条目已添加到 `docs/development_memory.md`
- [ ] 如果已有类似问题，已添加引用而非重复
- [ ] 解决方法已验证（可复现且一致修复）
- [ ] 后续方案将在相关时引用此条目
