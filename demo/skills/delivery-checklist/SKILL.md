# 交付检查清单

## 概述

实现完成后，本技能管理交付阶段。Agent 必须自测、编写结构化交付说明、逐项确认检查清单、更新问题记录，之后才能认为任务完成。

## 何时使用

**适用场景：**
- 按方案的代码实现已完成
- 准备交付并呈现结果给用户

**不适用：**
- 实现过程中的中间检查点
- 编写初始方案（使用 `plan-before-code`）
- 开发过程中记录问题（使用 `problem-tracking`）

## 流程

### 第一步：自测

交付前进行基本验证：

- **构建验证：** 如适用，编译/安装成功
- **冒烟测试：** 运行并检查基本功能
- **方案对照：** 确认方案中的所有条目已实现
- **无回归：** 确认现有功能仍然正常

### 第二步：编写交付说明

使用 `references/delivery-format.md` 中的格式。交付说明必须包含：

| 章节 | 内容 |
|------|------|
| 修改目标 | 本次实现了什么 |
| 修改文件 | 完整路径列表 |
| 实际完成内容 | 实际做了什么 |
| 未做内容/未验证内容 | 明确说明有意省略了什么 |
| 问题记录更新 | 是否更新了 development_memory.md |
| 编译方法 | 编译/安装步骤 |
| 测试方法 | 具体测试步骤和预期结果 |
| 注意事项 | 后续维护需要关注的问题 |

### 第三步：完成交付检查清单

逐项确认所有条目后再宣布交付完成：

```
交付检查清单
├── 实现
│   ├── [ ] 只修改了方案中列出的文件
│   ├── [ ] 没有添加未确认的功能
│   ├── [ ] 代码在正确的层中
│   └── [ ] 公共接口有 Doxygen 注释
├── 测试
│   ├── [ ] 项目编译/安装成功
│   ├── [ ] 基本功能已验证
│   ├── [ ] 现有功能无回归
│   └── [ ] 交付说明中记录了测试方法
├── 文档
│   ├── [ ] 交付说明按格式编写
│   ├── [ ] 列出了所有修改文件
│   ├── [ ] 明确说明了未做的内容
│   └── [ ] 给出了后续维护注意事项
├── 问题记录
│   ├── [ ] 新问题已记录到 development_memory.md
│   ├── [ ] 问题编号遵循 YYYYMMDD-NN 格式
│   └── [ ] 每个问题的 6 个章节已填写
└── 最终检查
    ├── [ ] 所有清单项已确认
    └── [ ] 交付说明已呈现给用户
```

### 第四步：更新问题记录

如果在测试或实现过程中遇到任何新问题，使用 `problem-tracking` 技能将其记录到 `docs/development_memory.md`。

### 第五步：呈现给用户

将交付说明呈现给用户。用户确认收到后任务才算完成。

## 常见借口与反驳

| 借口 | 事实 |
|------|------|
| "编译过了，肯定没问题" | 编译通过 ≠ 正确。始终运行基本冒烟测试。编译只检查语法，不检查逻辑。 |
| "交付说明不写了，改动一目了然" | 没有书面说明就没有变更记录。未来调试依赖知道改了什么以及为什么。 |
| "没遇到新问题，问题记录就不用更新了" | 明确地写"无更新"很重要。这证明你检查过且没有遗漏，而不是忘了检查。 |
| "测试步骤太基础了不值得写" | 基础测试步骤建立了一个基线。它们是以后出问题时第一个要检查的东西。 |
| "交付文档回头再补" | 交付文档在刚完成时最准确。延迟就会遗漏。 |

## 危险信号

- Agent 交付时没有书面说明
- 说明省略了"未做内容"章节（隐藏未完成的工作）
- 说明没有列出所有修改文件
- 问题记录章节写"无更新"但实现过程中确实遇到了错误
- 测试方法章节为空或写"在我机器上能跑"
- 清单项目被跳过而没有解释

## 验证

完成交付流程后：

- [ ] 项目构建成功（编译语言）
- [ ] 冒烟测试通过（基本功能正常）
- [ ] 交付说明已按格式编写，包含所有必需章节
- [ ] 所有修改文件已在说明中列出
- [ ] "未做内容"章节明确说明了省略的项目
- [ ] 问题记录更新状态已说明（即使"无更新"）
- [ ] 编译方法已记录
- [ ] 测试方法及具体步骤已记录
- [ ] 交付说明已呈现给用户确认
