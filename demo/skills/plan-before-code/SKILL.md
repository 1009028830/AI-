# 先写方案再编码

## 概述

在写任何代码、配置或脚本变更之前，必须先创建 Markdown 方案并经过用户审批。本技能定义了完整的"先写方案再编码"工作流：理解需求 → 查阅历史问题 → 编写方案 → 提交审核 → 等待确认。

## 何时使用

**适用场景：**
- 开始任何代码开发、功能新增或 bug 修复
- 修改配置、脚本、启动方式或部署方式
- 修改协议字段、默认参数或通信行为
- 调整文档目录结构或大范围重写 README

**不适用：**
- 纯对话或信息咨询类请求
- 仅阅读文件或搜索代码而不做修改

## 流程

### 第一步：理解需求

在编写方案之前，先明确要做什么：
- 要实现什么功能
- 修改哪个模块
- 是否涉及 UI
- 是否涉及通信、数据保存或配置
- 是否影响现有功能
- 是否需要兼容现有接口

如果需求不明确，提出问题澄清。如果必须做出合理假设才能继续，在方案中明确标注：`当前假设：xxx | 待确认：xxx`。

### 第二步：阅读历史问题记录

在编写方案之前，先阅读 `docs/development_memory.md`。重点关注：
- 以前是否遇到过类似问题
- 是否有已验证的解决方法
- 是否有容易出错或禁止修改的文件/模块
- 是否有特殊环境依赖、构建/运行/部署注意事项

### 第三步：编写方案文档

在 `docs/history_plans/` 中创建方案，参照 `references/plan-template.md` 模板。方案至少包含：

| 章节 | 内容 |
|------|------|
| 需求说明 | 要实现什么 |
| 当前现状 | 现有的代码、模块、文件 |
| 历史问题参考 | development_memory.md 中的相关条目 |
| 实现目标 | 完成后的状态 |
| 文件修改范围 | 新增文件、修改文件、不修改的文件 |
| 实现流程 | 步骤化逻辑 |
| 测试/验证方法 | 如何验证正确性 |
| 待用户确认事项 | 需要用户决策的内容 |

### 第四步：提交用户审核

将方案呈现给用户。不要开始实现。等待明确确认。

### 第五步：确认后再继续

只有在用户明确确认方案后才能开始写代码。如果方案需要修改，先修改再重新确认。

## 常见借口与反驳

| 借口 | 事实 |
|------|------|
| "这个改动太小，不需要方案" | 小改动在假设错误时同样会造成大问题。5 行方案永远比错误假设的调试成本低。 |
| "我已经理解需要做什么了" | 没有书面方案的理解不可靠。写下来才能强制清晰思考。方案也是后续参考的文档。 |
| "我快速写个方案然后直接开始编码" | 审核步骤至关重要。用户审核能发现需求误解，在写代码前修正的成本是指数级降低的。 |
| "实现方案显而易见" | Agent 眼中的"显而易见"可能与用户实际想要的不一致。方案能暴露隐藏假设。 |

## 危险信号

- Agent 在没有先创建方案的情况下开始写代码
- 方案写了但与代码改动一起提交
- 方案省略了历史问题参考章节
- 方案没有明确列出不修改的文件
- Agent 在没有用户明确确认的情况下继续

## 验证

完成本技能流程后：

- [ ] 在编写方案前已阅读 `docs/development_memory.md`
- [ ] 方案文档已写入 `docs/history_plans/`
- [ ] 方案包含所有必需章节（需求、现状、历史问题、目标、文件范围、测试方法、确认事项）
- [ ] 方案已提交用户审核
- [ ] 用户在代码写入前已明确确认方案
- [ ] 如需修改，方案已修改并重新确认
