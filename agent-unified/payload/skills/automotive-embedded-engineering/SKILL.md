# 车载嵌入式工程

将 OEM 需求、软硬件接口、代码和测试证据连接起来。此技能是工程工作流与检查项，不是标准全文、认证结论或对真实车辆的操作授权。

## 先确定适用基线

从当前项目读取 ECU 职责、车型/销售市场、MCU/SoC、硬件版本、启动链、RTOS/Linux/AUTOSAR 版本、编译器与生成工具、诊断和网络数据库版本。涉及安全时读取已批准的安全目标、ASIL 分配、故障容错时间和安全状态；没有这些输入时保留缺项，不凭 ECU 名称指定 ASIL。

确定 OEM 合同采用的标准版次、修订/修改单和偏离流程。新发布版次仅触发差异评估，不自动改写量产项目接口。标准目录中的题录确认不代表已读全文。

## 按任务加载

- C/C++、RTOS、驱动、通信、诊断、升级或代码评审：读取 [工程规则](references/engineering-rules.md) 的对应小节。
- AUTOSAR、MISRA、功能安全、网络安全、过程或 EMC 选型：读取 [规范与来源](references/standards.md)。
- 需求追溯、测试计划、评审交付：读取 [验收与证据](references/verification.md)。
- 若为电池控制器，额外使用已安装的 `battery-bms-engineering`；若涉及 STM32、ESP-IDF 或 Linux 驱动，再按实际平台选对应技能。不假定这些技能在目标机器已经存在。

## 实施约束

1. 从需求与接口定位最小影响范围，区分手写代码、生成代码、标定数据和供应商黑盒；生成代码改源配置并重新生成。
2. 明确任务/ISR 调用上下文、截止期、资源所有权与跨核共享方式，再改调度或同步逻辑。Linux 用户态结果不能外推为硬实时保证。
3. 通信解析与控制动作分离，输入带有效性与新鲜度。发送成功、协议应答、物理反馈、业务完成分别判断。
4. 诊断写入、例程、重编程和执行器控制按现有动作授权与目标状态执行；先完成离线分析和模拟验证，不在未知车辆上试探。
5. 安全机制、网络安全机制和可用性一起审查。CRC/E2E 不等于身份认证；加密或 SecOC 也不能替代功能安全分析。
6. 静态分析使用项目指定的语言标准、编译目标和规则配置。记录不能自动检查的规则、工具覆盖差距与批准的偏离，不用零告警代替 MISRA 合规声明。
7. 保留软件、标定、DBC/ARXML/ODX、工具链和测试输入的版本关联；发布包与被测二进制一致。

## 完成判据

交付适用规则及不适用理由、具体代码/配置改动、已执行验证与证据位置、尚未验证的目标板/整车项目。安全相关缺项要指出阻断的结论；其余已授权工作继续推进。不宣称完成 ISO 26262、ASPICE 或整车型式认证。
