# Git/Gitee 协作与版本管理

版本：v1.1；更新日期：2026-10-26。

依据用户提供的《Gitee版本管理与测试方案.md》（2026-10-23）提炼，适用于 Windows/Linux 上的 Git 及 GitHub/Gitee 协作。Git 是版本控制工具，平台权限、PR、CI/CD 和制品能力需分别核实。原方案中的示例不是执行命令、改远端设置或发布的自动授权。

## 1. 适用范围与授权

- 仅在提交、推送、PR、合并、分支管理、回退或发版任务中读取。仓库已有明确规则、维护分支与合并策略按其作用域优先；通用默认不能覆盖保护规则。
- 开始前核对 Git 根、工作区/暂存区、当前分支、远端 URL、跟踪关系、实际主干、目标分支和发布边界；多远端仓库不默认向所有远端同步。
- 按用户请求与同一任务上下文区分 commit、push、创建/更新 PR、merge、Tag、Release 和部署。已有明确授权继续有效；会话已明确“提交 Git”包含推送时沿用约定，不重复确认。仅本地提交要求不得扩大为远端写入。
- 用户已明确：个人独立工作默认直接提交、推送，只有多人协作或明确要求时创建 PR。不能因为本文包含 PR 流程就自动创建 PR 或工作分支；既有门禁阻止直推时说明原因，取得用户对后续方式的选择，不绕过保护。
- “更新提交规则”授权规则落地，不自动授权修改远端保护、安装 hooks、创建 Issue、发通知、提交/推送当前修改或发布版本。提交与 PR 的授权也不自动包含合并、部署、历史重写或重要删除。
- 计划新增发布流水线前核对既有推送/Tag 是否会触发外部部署；不能通过提交信息关键字隐式获得部署权限。

## 2. 分支与流转

团队协作参考 Git Flow，但先识别项目已有模型，不按团队人数机械切换，也不为一次提交新建整套永久分支。个人工作使用当前已确认的提交/推送目标；以下分支流转中的 PR 仅在协作或用户明确要求时启用。

| 场景 | 起点与目标 | 要求 |
|---|---|---|
| 个人日常工作 | 当前已确认分支 → commit → push | 不自动创建 PR；按任务需要决定是否另建分支，遵守仓库保护限制 |
| 团队常规功能/缺陷 | `develop → feature/* → PR → develop` | 功能完整、检查通过后集成；普通缺陷不冒用紧急 hotfix |
| 标准发版 | `develop → release/* → main/master`，修复回流 `develop` | release 只稳定版本、修复缺陷；协作时经 PR，正式版本对应经过验收的提交 |
| 生产紧急修复 | 当前生产 Tag/维护主干 → `hotfix/*` → 对应主干及维护分支 | 先核实生产实际版本与合并方式；同步 develop，必要时同步活动 release，记录应急策略 |
| 已采用简化 Git Flow | `feature/* → develop → main/master` | 协作时经 PR，按现有发布门禁省略独立 release；保留质量与版本追踪 |
| 已有仅主干仓库 | 当前实际主干，或按任务需要的工作分支 | 个人工作按已授权目标提交/推送；协作或明确要求时走 PR，不假定 develop 存在 |
| 已采用主干开发或多维护分支 | 沿用现有短分支/特性开关/`support/*` 策略 | 模型迁移另立范围，不以本文重写共享历史 |

主干是仓库实际的 `main` 或 `master` 等分支，不同时维护两个名字相近的主干。个人工作是否可直接推送取决于当前授权和真实仓库限制；若保护规则或项目门禁强制要求 PR，说明阻挡原因并取得对应选择，不擅自开 PR 或放宽门禁。应急例外须符合仓库既有策略与当前动作授权，不自行关闭保护。

分支名称使用小写 ASCII、短横线和清晰类别，例如 `feature/alice-can-timeout-20261026`、`release/v1.2.0-20261026`、`hotfix/bug-1001-timeout-20261026`、`docs/git-workflow`。作者和日期可按仓库约定保留；Issue 的原始大小写标识在提交/PR 正文中准确关联。名称须通过 Git ref 规则及平台/CI 限制，不把某个平台的字符或长度限制当作 Git 通则。

## 3. 本地提交

1. 明确本次变更与验收，读取已有有效验证。沿用“编译/基础检查 → 相关功能验证 → 一轮集中审查”，修复只复核受影响项；具体规则见 [验证与审查](../skills/verification-and-review/SKILL.md)。
2. 核对工作区与暂存区，按明确文件或补丁块暂存；检查暂存差异、秘密/个人数据、生成产物、大文件及第三方分发边界。不要使用宽泛的 `git add .` 把无关文件一并纳入。
3. 一个提交表达一个完整意图；不能为凑小提交把必要代码与对应测试拆成无法工作的中间状态。相关大变更可按可验证步骤拆分。
4. 使用 `type(scope): subject`；scope 可省略，允许 `type(scope)!: subject`。默认类型为 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`style`、`perf`、`revert`、`build`、`ci`，标题简洁说明实际变化；正文按需写原因、兼容性、工单与验证。
5. 不兼容变化用 `!` 或 `BREAKING CHANGE:` footer 标识，并说明受影响接口、迁移方法与兼容策略。Conventional Commits 允许自定义类型，仓库若采用白名单，提交模板、校验器、自动化触发须一致。[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)
6. 已有需求/缺陷单准确关联。缺陷通常先建单或关联再修；无平台权限或紧急止损时先保留可追溯本地记录，按项目门禁补单或说明例外。不虚构编号，不把新增外部工单当作规则编辑的默认副作用。docs/chore 等无工单时说明原因即可。

示例：

```text
feat(can): 增加报文超时状态上报
fix(bms): 修复故障复位后的状态同步
docs(workflow): 明确提交与发布的授权边界
chore(release): 准备 v1.2.0 发布说明
feat(protocol)!: 调整消息版本字段

BREAKING CHANGE: 接收方必须识别新版本字段；升级前按协议迁移说明完成兼容验证。
```

这里展示多个独立标题，footer 仅属于最后一个示例。平台自动生成的 merge 标题、`git revert` 的默认标题及机器人提交，应有明确兼容策略；可以按项目要求使用合规标题，也可以对确定的自动生成场景单独校验，不能为通过格式检查更改提交语义。Squash 后的新标题单独校验，不能只检查 PR 中间提交。

## 4. 增量检查与提交范围

提交信息检查只检查此次引入的提交，不翻历史旧账，也不为修复旧格式改写已共享提交。pre-push 的输入语义与 `A..B` 可达提交范围见 [Git hooks](https://git-scm.com/docs/githooks#_pre_push) 和 [Git revisions](https://git-scm.com/docs/gitrevisions#_specifying_ranges)。下表定义规则验收范围，不等同于网络实际传输的对象集合。

| 场景 | 比较与处理 |
|---|---|
| commit-msg | 当前提交消息文件；检查首行及必要 footer，不把正文任意一行匹配成功当作标题通过 |
| 已存在远端分支的快进推送 | 已核实的远端旧 tip 到本地新 tip，即 `old..new`；先确认对象存在及推送关系 |
| 新建远端分支 | 远端旧 OID 为零时，选择并获取明确的目标集成分支/创建基线，计算其到新 tip 的新增提交；不能退化为 `git log <new-tip>` 扫全部祖先 |
| PR 更新 | 使用当前目标分支与源分支计算新增提交；同时核对平台实际测试的 head 或 merge-result SHA |
| 删除 ref | 没有新增提交消息可查，但删除权限、合并状态和未推送工作仍须核对 |
| Tag 推送 | 按发布策略核对 Tag、指向提交及发布证据，不把 Tag 对象当普通分支提交范围 |
| 基线缺失、浅克隆或无共同历史 | 补齐所需对象或明确记录无法验证；不声称检查通过，不静默扩大成全历史检查 |

“此次推送引入仓库的提交”与“相对 PR 目标分支的提交”是不同集合。实现 hooks/CI 时须声明采用哪一种，必要时排除该远端已经可达的提交；不可随便使用另一远端或陈旧缓存当基线，也不固定假定 SHA-1 的 40 位长度。

优先使用项目已有校验器；若新增自动化，选择跨平台实现与明确正则引擎，覆盖 scope、`!`、footer、首行空白、merge/revert、新 ref、删除 ref、Tag 及浅克隆等适用边界。不要把 Python 风格的 `\w`/`\s` 不经核对复制进 POSIX `grep -E`。本文不安装或替换 hooks。

## 5. PR、评审与 CI

本节仅在多人协作或用户明确要求 PR 时启用；普通个人提交不自动进入 PR 流程，既有 CI 仍按实际触发配置运行。

- 协作时同仓库工作分支走 PR；外部贡献按仓库允许的 Fork 流程。描述写明问题、最终行为、影响范围、实际验证、风险与回退；不复制无关会话过程。
- 自动化先完成相关基础与功能检查，再做一轮集中审查；只读设计讨论、必要执行前安全审查与环境缺失时的静态审查不被此顺序阻断。PR 可以先建为草稿，检查未完成时不宣称可合并。
- PR 门禁包括适用的必需 CI、阻断问题解决及指定人工评审。默认团队流程至少一名指定评审者；实际人数、代码所有者、紧急与单人项目策略以已明确规则为准。Agent 审查不能冒充人工批准。
- CI 必须对应当前 head 及项目要求的合并结果。更新后重跑失效/受影响检查，复核新增差异；源分支检查通过不保证合并后行为正确，若目标基线变化，应按项目合并验证策略重新核对。
- 本地只做提交/推送且输入未变时复用有效检查；远端必需 CI 仍要满足。平台自动触发检查不等于需要再在本地重复全套。
- 文档只做相关格式/链接/规则检查；业务变更做相关单元与集成验证；跨模块、驱动、协议、保护逻辑或 release 验收按影响与门禁扩大。覆盖率目标、PR 大小和响应时限是项目策略，不把“80% / 400 行 / 24 小时”作为所有工程的通用硬门槛。
- “通过”“失败”“取消”“跳过”“未运行”分别记录。只有仓库接受的必需检查与审批满足才合并；不能把跳过或旧版本成功直接当成通过。
- 评审意见区分阻断、建议、疑问，围绕代码与依据；评审中的共享分支默认增加修复提交，避免 rebase/force push 丢失上下文。不把普通提交授权扩大为历史重写。

可在仓库已有 PR 模板中采用以下字段；模板路径、Issue 关联与关闭关键词遵循具体平台，不保证只写 `#编号` 就会自动关闭：

```markdown
## 问题与目标
说明需求/缺陷；关联已有工单，无工单时注明原因。

## 改动与影响
说明最终行为、受影响接口和必要兼容措施。

## 验证
列出实际命令/操作、环境、结果与覆盖范围；标明跳过和未验证项。

## 风险与回退
说明发布顺序、数据/协议兼容、回退步骤及待完成门禁。
```

## 6. 合并、版本与回退

- feature 采用仓库统一的 squash 或 merge 策略。Git Flow 的 release/hotfix 通常保留合并节点并回流 develop；已强制线性历史的项目沿用其策略，不为套用 `--no-ff` 关闭保护。
- 正式版本使用 SemVer；Git Tag 按约定加 `v` 前缀，例如 `v1.2.0`，候选版使用 `v1.2.0-rc.1`。主/次/修订号按公共兼容性语义确定，不以提交数量猜版本号。[SemVer 2.0.0](https://semver.org/lang/zh-CN/)
- 发版前核对批准范围、目标提交、验收、CHANGELOG、构建环境和制品校验值。正式 Tag 指向被验收的主干提交；预发布 Tag 的分支位置按项目约定。优先附注 Tag，需签名时使用已配置密钥。
- CHANGELOG 沿用项目格式；无既有格式时按 Added / Changed / Fixed / Deprecated / Removed / Security 归类用户可感知变化，不直接堆叠 Git 日志。[Keep a Changelog 1.1.0](https://keepachangelog.com/zh-CN/1.1.0/)
- Tag、Release、制品上传和部署分别核对授权与结果；禁止移动已发布 Tag 来覆盖错误版本。错误修正发新版本，不能把“每次合并打 Tag”理解成每个开发 PR 都发布。
- 触发发版优先采用受控 Tag/审批流程；若沿用提交信息触发，类型白名单和触发条件要一致，例如允许 `chore(release): ...`。只有关键词匹配不构成发布授权，也不能绕开验收。
- 共享历史中的错误优先 `git revert`，合并提交先核对主线与后续影响，再经必要验证/PR；这不保证数据库、设备固件或已部署服务自动回滚。部署旧 Tag 前仍须检查数据与协议兼容。
- 本地未发布的错误优先保留工作后调整；`reset --hard`、强推、删除 Tag/分支和历史迁移需相应明确授权。保护分支不强推；私人分支确需改写时也先核对协作者、远端状态和批准范围。
- 临时分支在相关合并/回流完成、无未推送工作且已有清理授权后删除。没有确认合并就不能只按分支名前缀批量清理；未完成 PR 或有效维护分支保留。

## 7. 大文件、hooks 与平台适配

- 源码、规则、必要小型夹具进入 Git；大型安装包/工具镜像优先制品仓库或按授权管理的 Release 资产。私有配置、凭据与业务数据不能因启用 LFS 而进入公开仓库。
- 按实际 Gitee/GitHub 套餐、容量、带宽、单文件限额与权限判断 LFS 是否适用；不把参考方案中的收费与容量数字写成长期保证。
- LFS 指针提交和对象上传是两件事。必须确认相应对象可上传、可获取；`git push --no-verify` 会跳过整个 pre-push，不能作为正常跳过 LFS 上传的方法，避免远端只有无法取回内容的指针。[Git push](https://git-scm.com/docs/git-push#Documentation/git-push.txt---no-verify)、[Git LFS pre-push](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-pre-push.adoc)
- 接入 `.githooks` 或 `core.hooksPath` 前先查看现有配置和 hooks；保留 LFS 与团队既有逻辑，按当前 LFS 官方方式整合，不用新校验器覆盖已有 pre-push。需要手动整合时可查看 `git lfs install --manual`；自定义检查若消费 stdin，必须确保 LFS 仍收到完整的 ref 输入。新增 hooks/配置需在任务范围内实施和验证。[Git LFS install](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-install.adoc)
- Gitee Go 与 GitHub Actions 的 YAML、PR 状态接入、保护规则、评审模式、Issue 状态联动按当前官方文档和仓库版本适配，不原样复制平台专属示例。Gitee 的评审模式只有在目标仓库已启用、成员符合对应权限条件时才采用，不能把正常 push 一概视作自动创建 PR。[Gitee 保护分支](https://help.gitee.com/repository/branch/protected-branches)
- 工单的文本引用、主动关联与关闭分别核对意图和权限。Gitee 官方说明主动关联 PR 可能改变 Issue 状态、合并后关闭；建立关联前核实真实目标与副作用，不推广为所有平台的行为，完成后以实际状态确认。[Gitee PR 关联 Issue](https://help.gitee.com/base/pullrequest/issue)

## 8. 交付与停止条件

必要检查通过、阻断项解决且授权覆盖目标动作后推进。仅提交报告实际 commit；推送后核对远端目标 ref；创建 PR 后返回其链接与门禁状态；发版后核对 Tag、Release 与产物，不把某一步成功推断为整条链完成。

没有新改动或风险时停止，不为准备提交再次做整套代码审查。平台或权限不足时交付已完成的本地成果及具体未完成动作，不伪造远端结果。

## 9. 来源与适用性

用户方案用于确定协作偏好；后续明确的“个人提交不自动创建 PR”要求优先于原方案的默认 PR 流程。Git、提交规范及平台行为通过官方资料核对。查询日期：2026-10-26。实际应用仍以当前工具版本、仓库规则和平台配置为准。

正文链接均为本次已读取的规范维护方、Git/Git LFS 上游或 Gitee 官方资料。补充入口：[Git ref 命名规则](https://git-scm.com/docs/git-check-ref-format)、[Gitee PR 检查门禁](https://help.gitee.com/base/pullrequest/ci-check)、[Gitee LFS](https://help.gitee.com/enterprise/code-manage/code-hosting/large-file-manage/git-lfs)。

本次没有验证特定账号的套餐/容量、企业保护规则优先级、Gitee Go 当前 YAML schema 或目标仓库门禁设置；落地这些配置时再核实。用户原方案的完整正文与示例脚本保留在其原文件，本文是经整合的通用规则，不复制平台配置为可执行保证。
