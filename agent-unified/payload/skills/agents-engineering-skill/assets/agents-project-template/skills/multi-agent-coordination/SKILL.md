# 按需多智能体协作

## 启用与分工

本技能明确请求：在任务满足上述触发条件且当前客户端支持时，使用子智能体处理独立子任务。先确认可用工具、角色和并发额度；高优先级规则与用户当前范围始终优先。没有工具时由主智能体分步骤完成，不能声称已运行多个智能体。

主智能体负责范围、共享接口、文件所有权、集成和最终结论。普通独立任务通常启用 1–2 个子智能体，默认同时最多 3 个子智能体且不超过客户端上限；这是一项用量策略，不是提高客户端额度。子智能体不自行再次委派。

优先并行只读调研、影响分析和测试准备。并行代码修改必须有互不重叠的文件所有权；公共接口先确定，一个文件同一时间只有一个修改者。共享工作区不是隔离沙箱；必要时使用独立工作区，但不为小任务机械创建。

按能力选已安装角色：`architecture_explorer`、`docs_researcher`、`software_worker`、`firmware_worker`、`linux_worker`、`test_engineer`、`code_reviewer`、`protocol_safety`。只选当前需要的角色，不把角色目录当执行清单。角色缺失时使用客户端已有子智能体并明确职责，不虚构自定义角色已加载。

## 委派契约

每个子任务简短给出：

- 目标、验收条件及必要上下文入口。
- 只读或可写；拥有的文件和共享接口；禁止修改的范围。
- 前置依赖、已有验证证据，以及由谁执行哪些检查。
- 预期输出、完成条件和需要向主智能体报告的阻塞项。

主智能体继续独立工作，不重复执行已委派的工作。只共享完成任务必要的信息；凭据通过现有安全配置使用，不粘贴到子任务消息。子智能体不能扩大发布、联网写入、依赖新增或设备动作授权。

## 集成、验证和审查

1. 测试设计可与实现并行；依赖构建的测试等待对应代码稳定和构建成功。
2. 主智能体先整合改动、解决接口冲突，再确认针对集成版本的编译/基础检查和相关功能验证。子模块分别通过不代表集成通过。
3. 验证证据说明命令、环境、实际输入/版本、产物、结果和覆盖范围。有效证据共享；输入、配置、环境或外部状态变化使相关结果失效。
4. 必要检查通过后，通常交给一个 `code_reviewer` 集中审查本次差异。高风险时增加范围不重叠的专项；执行前安全核对必须前置。
5. 修复只重跑受影响检查，并让原审查者复核修复差异和关联风险。未改部分不重新完整审查；交付阶段只汇总。

详细顺序与例外沿用 [验证与审查](../verification-and-review/SKILL.md)。文档变化采用结构/引用检查，只读评审不以先构建为条件；测试与多方一致意见都不能代替真实目标环境证据。

## 回报与停止

子智能体返回结论、文件变化或来源、验证证据、未解决项与未覆盖风险，避免贴完整日志。卡住时报告原因，不无界重试、不自行扩展范围。

主智能体核对矛盾并对最终版本负责；子任务失败或取消不是完成。已有足够证据、相关检查通过且阻断项解决就停止；及时结束无用工作，不为凑角色数继续委派。
