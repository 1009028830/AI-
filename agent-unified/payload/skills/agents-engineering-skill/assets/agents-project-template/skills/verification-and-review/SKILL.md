# 验证与审查

## 先确定检查范围

- 只读评审围绕用户指定范围阅读代码；没有运行证据需求时不运行测试或构建。
- 普通文档、注释只核对差异、引用与格式；可执行示例、生成内容或构建行为变化补充相应检查。
- AGENTS/技能变化核对结构、链接、触发边界、规则冲突与相关使用场景，不自动触发业务全量测试。
- 小型代码修改核对差异、直接调用关系和相关测试；简短记录命令、环境、结果即可，不要求验证矩阵或五轴审查。
- 公共接口、共享依赖、跨模块行为、驱动、协议、BMS 保护、安全或生产变化，按影响范围补充回归、边界与失败路径；多项风险需对照时才用验证矩阵。

## 默认执行顺序

常规实现采用以下顺序；初始范围确认与必要设计分析不算每轮正式代码审查。

1. **编译或基础检查**：先运行相关构建；解释型代码采用项目适用的语法、类型或导入检查。失败先定位和修复，不启动后续依赖阶段或整套审查。
2. **验证行为**：基础检查通过后，验证验收主路径、关键边界、主要失败路径及受影响回归。缺陷修复先建立能复现问题的测试；不必等最终编译成功才编写测试。已有有效证据直接复用。
3. **集中审查**：必要检查通过后，对本次稳定改动及必要上下文做一轮审查，重点核对测试遗漏、并发、资源生命周期、接口和安全风险，以及测试本身是否有效；不重做前阶段已完成的机械检查。
4. **修复与增量复核**：审查发现问题时修复，重跑受影响构建/测试，再复核修复差异及关联风险；其余已审查且未受影响部分沿用结论。影响扩大、证据失效或明确门禁要求时扩大范围，不能用“一轮”限制阻止必要复核。
5. **结束**：适用检查通过且阻断问题解决后交付；没有新变化时不因阶段切换再次审查或测试。

编译通过不能证明逻辑正确，测试通过只说明已覆盖的验收场景通过。普通文档和规则修改用前述结构/引用检查代替编译与业务测试。用户明确要求的只读评审直接进行；环境缺失时可以先做静态审查，但说明未运行的检查，不能宣称已完成运行验收。真实设备、生产写入或破坏性测试前必须先完成必要安全审查及动作授权，不能拖到执行后。

## 复用证据与停止

项目已有 `verification.json` 与 `scripts/verify.py` 时，优先通过该入口预览并运行相关任务，避免重新拼接测试命令。需要接入新场景或修改配置时才读取项目根的 `references/incremental-verification.md` 与 `references/verification-scenarios.md`；不要因普通问答自动运行。既有检查命令和明确门禁仍是实际验收依据。

同一任务内，已有命令、结果和覆盖范围可追溯，且相关源码、测试、依赖、构建配置与运行环境未变时复用结果。提交号相同不代表工作区未变；发现不稳定测试、外部状态变化或证据不足时重新验证。

后续修改只使受影响的证据失效。总检查入口已包含的子检查不再单独重复执行。必要检查通过且没有新风险证据后停止；交付和 Git 提交阶段只汇总已有有效结果，项目明确门禁仍须满足。

全量检查仅在影响范围、明确门禁、发布要求或用户请求需要时执行，可交给 CI；核对 CI 对应的版本、检查范围与环境，不能用模拟或其他平台结果代替目标环境验收。

## 处理失败

保留原始错误，区分本次回归、已有失败、环境限制和测试问题；修复根因后重跑受影响检查。未解决失败不得标成通过，无法验证的范围说明原因。

## 按风险审查

始终确认修改符合目标、范围明确且没有明显错误。仅展开与本次变化相关的维度：

- 正确性：验收、边界、错误路径与回归。
- 可读性：命名、控制流、重复与复杂度。
- 架构：公共接口、模块边界与依赖方向变化。
- 安全：输入、权限、密钥、资源及依赖风险。
- 性能：有证据的瓶颈、无界操作、阻塞或资源使用变化。

用户要求全面评审或跨领域高风险变化时才逐项审查。问题按阻断、重要、建议说明文件与依据。

## 完成与交付

涉及标准或高风险交付时，按需对照项目根的 `references/definition-of-done.md`；已读取且未变化时不重复加载。只核对适用项，不把清单当成新测试触发器。将有效证据与未覆盖范围交给交付阶段，不重新启动检查。
