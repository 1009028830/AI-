# 使用开发工作流

## 路由

```text
任务到达
  ├─ L0 只读分析 -> 直接回答，必要时 project-analysis / context-loading
  ├─ L1 小型可逆 -> 简短说明 -> 修改 -> 聚焦检查 -> 简短交付
  ├─ L2 标准改动 -> project-analysis -> plan-before-code -> 用户确认
  │                                      -> minimal-implementation
  │                                      -> verification-and-review
  └─ L3 高风险   -> L2 + source-verification + 风险/兼容/回退/目标环境验证

按需插入：
  异常定位 -> problem-tracking
  可复用自动化 -> reuse-scripts
  复杂交付 -> delivery-checklist（只汇总证据）
```

## 分级判定

- **L0：** 不写文件、不改变外部状态。
- **L1：** 通常 1–2 个文件，可轻易回退，不改变公共接口、数据、依赖、安全、权限或部署。
- **L2：** 新功能、Bug 修复、跨文件重构、配置/脚本/大范围文档变化。
- **L3：** API/协议、数据迁移、安全、权限、硬件控制、生产部署、破坏性或不可逆动作。

按实际影响和后果分级，不以文件数量或轻微不确定性自动升级；先做最小只读核实。涉及安全、数据或设备后果的关键不确定性按高风险处理。任务执行中一旦出现更高风险，停止扩展，更新方案与授权。

## 通用行为

1. 先读适用的 AGENTS 与 Git 状态。
2. 明确目标、范围、假设、风险和验证方法。
3. 只加载当前步骤所需资料，不把全部规范和技能塞入上下文。
4. 对明显有问题的做法指出具体后果并给出替代方案。
5. 保持范围纪律，不删除不理解的内容，不做顺手重构。
6. 用证据验证；区分静态、本地、沙箱、硬件和生产结果。
7. 同一任务内相关输入和环境未变时复用可追溯结果；检查通过后停止，阶段切换不重启全流程。

## 停止条件

- 权威来源相互冲突且会改变实现。
- 方案外文件或新依赖成为必要条件。
- 需要新的外部权限、破坏性操作或生产动作。
- 目标环境无法获得，而验收必须依赖该环境。

停止时报告已确认事实、冲突、缺少的信息与最小下一步。

## 验证

- [ ] 已确定任务级别与适用 skill。
- [ ] 没有让 L0 任务产生文件改动。
- [ ] L2/L3 已有持久方案和明确确认。
- [ ] 验证强度与风险相匹配。
- [ ] 未把未验证推断写成完成结论。
