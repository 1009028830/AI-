# 先写方案再实现

## 流程

### 1. 定义边界

明确要做什么、影响哪些模块、是否涉及接口/数据/配置/UI/部署、是否需要兼容旧行为。仅在关键歧义会改变结果、成本或风险时澄清，其余采用合理假设继续。

写明：

- 目标与明确不做事项。
- 输入、输出、兼容性和验收标准。
- L2/L3 判定依据。
- 关键假设；影响实现的歧义应先澄清。

### 2. 加载必要上下文

编写方案前，项目存在以下问题记录时按需读取：

```text
docs/development_memory.md
```

再按 `context-loading` 读取知识地图、相关实现、调用方、测试和权威来源。记录是否有历史问题与规则冲突。

已有对应方案时更新或引用，不为新一轮对话重复创建。项目没有相关文档时说明事实，不假定文件存在，也不为普通任务另建文档系统。

### 3. 编写方案文档

在 `docs/history_plans/` 中创建方案，参照：

```text
references/plan-template.md
```

推荐命名：

```text
docs/history_plans/YYYYMMDD_功能名称_开发方案.md
```

方案必须包含：

- 状态、版本、创建日期、授权来源及覆盖范围。
- 需求说明、当前现状、历史问题参考。
- 实现目标、文件修改范围、不修改范围。
- 实现流程、错误处理、测试/验证方法。
- 风险、兼容性、回退方法和目标环境验证边界。
- 尚未覆盖的关键选择或授权事项；没有时明确说明已有授权足够。

文件修改范围必须包含固定例外：如果实现、编译、运行或测试过程中遇到新问题，允许按 `problem-tracking` 更新 `docs/development_memory.md`。

每个实现任务应尽量形成薄垂直切片，包含验收、文件与验证方法。

### 4. 核对授权并推进

先核对当前任务和此前对同一范围的明确授权。用户已要求实施、或明确同意所提建议，且计划未实质扩大范围或增加未授权动作时，记录依据后继续实现，不要求用户重复回复固定确认语句。

只有缺少会改变结果的关键选择、所需权限/动作授权，或计划实质扩大范围与风险时，才请求确认。先完成已授权且可独立进行的准备，说明具体待确认事项及原因；等待期间不执行依赖该确认的动作。用户明确要求“方案另行审批”时，仍在对应阶段等待，不能把普通实施授权扩大为发布、设备或不可逆动作授权。

## 验证

- [ ] 已按需读取项目实际存在的问题记录，未假定缺失文件存在。
- [ ] 方案已写入 `docs/history_plans/`。
- [ ] 方案列出新增、修改、不修改文件。
- [ ] 方案包含测试/验证方法。
- [ ] 方案包含风险、回退和验证边界。
- [ ] 任务切片可独立验证。
- [ ] 已核实授权来源和覆盖范围；只对未覆盖事项取得必要确认。
