# 按需规划与实现边界

## 流程

### 1. 定义边界

明确要做什么、影响哪些模块、是否涉及接口/数据/配置/UI/部署、是否需要兼容旧行为。仅在关键歧义会改变结果、成本或风险时澄清，其余采用合理假设继续。

写明：

- 目标与明确不做事项。
- 输入、输出、兼容性和验收标准。
- L2/L3 判定依据。
- 关键假设；影响实现的歧义应先澄清。

### 2. 加载必要上下文

编写方案前，项目存在以下问题记录时按需读取：

```text
docs/development_memory.md
```

再按 `context-loading` 读取知识地图、相关实现、调用方、测试和权威来源。记录是否有历史问题与规则冲突。

已有对应方案时更新或引用，不为新一轮对话重复创建。项目没有相关文档时说明事实，不假定文件存在，也不为普通任务另建文档系统。

### 3. 选择方案形式

普通 L2 任务可在聊天中用简短方案说明目标、影响范围、实现步骤、验收与相关检查；已有说明足够时直接引用。文件数量、Bug/脚本等任务名称不决定是否创建方案文件。

跨模块公共接口或协议需要协作约定、高风险变更需要回退与执行记录、任务需要跨会话或多人衔接，或用户/项目明确要求时，保存必要方案。优先更新已有对应文档；没有合适位置时再使用 `docs/history_plans/YYYYMMDD_功能名称_开发方案.md`。

持久化方案按需选用 [方案参考](../../references/plan-template.md) 的相关章节，不整份复制、不为未涉及项逐一填写“不适用”。方案围绕当前任务覆盖：

- 目标、影响范围、实现步骤与验收方法。
- 涉及的接口、兼容性、错误路径及对应验证。
- 实际存在的风险、回退条件和目标环境限制。
- 尚未解决的关键选择或授权边界；已有授权不重复索取。

复杂实现可拆成可验证的小步。只有具有复用价值的问题才按项目约定记录，不在每份方案中预设固定问题记录例外。

### 4. 核对授权并推进

先核对当前任务和此前对同一范围的明确授权。用户已要求实施、或明确同意所提建议，且计划未实质扩大范围或增加未授权动作时，记录依据后继续实现，不要求用户重复回复固定确认语句。

只有缺少会改变结果的关键选择、所需权限/动作授权，或计划实质扩大范围与风险时，才请求确认。先完成已授权且可独立进行的准备，说明具体待确认事项及原因；等待期间不执行依赖该确认的动作。用户明确要求“方案另行审批”时，仍在对应阶段等待，不能把普通实施授权扩大为发布、设备或不可逆动作授权。

## 验证

- [ ] 已按需读取项目实际存在的问题记录，未假定缺失文件存在。
- [ ] 方案形式与任务需要匹配，普通任务未被要求额外生成文档。
- [ ] 已明确目标、影响范围、验收及相关验证；复杂任务可分步验证。
- [ ] 需要保存的方案已在合适位置记录，并覆盖实际风险、回退和验证边界。
- [ ] 已核实授权来源和覆盖范围；只对未覆盖事项取得必要确认。
