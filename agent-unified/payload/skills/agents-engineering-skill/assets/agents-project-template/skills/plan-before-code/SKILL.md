# 先写方案再实现

## 流程

### 1. 定义边界

明确要做什么、影响哪些模块、是否涉及接口/数据/配置/UI/部署、是否需要兼容旧行为。需求不清时先提出澄清问题。

写明：

- 目标与明确不做事项。
- 输入、输出、兼容性和验收标准。
- L2/L3 判定依据。
- 关键假设；影响实现的歧义应先澄清。

### 2. 加载必要上下文

编写方案前阅读：

```text
docs/development_memory.md
```

再按 `context-loading` 读取知识地图、相关实现、调用方、测试和权威来源。记录是否有历史问题与规则冲突。

### 3. 编写方案文档

在 `docs/history_plans/` 中创建方案，参照：

```text
references/plan-template.md
```

推荐命名：

```text
docs/history_plans/YYYYMMDD_功能名称_开发方案.md
```

方案必须包含：

- 状态、版本、创建日期、确认记录。
- 需求说明、当前现状、历史问题参考。
- 实现目标、文件修改范围、不修改范围。
- 实现流程、错误处理、测试/验证方法。
- 风险、兼容性、回退方法和目标环境验证边界。
- 待用户确认事项。

文件修改范围必须包含固定例外：如果实现、编译、运行或测试过程中遇到新问题，允许按 `problem-tracking` 更新 `docs/development_memory.md`。

每个实现任务应尽量形成薄垂直切片，包含验收、文件与验证方法。

### 4. 提交用户审核

写完方案后停止，不开始实现。只有用户回复“确认按此方案执行”“批准方案”“可以开始实现”等明确授权语句，才进入实现阶段。

## 验证

- [ ] 已阅读 `docs/development_memory.md`。
- [ ] 方案已写入 `docs/history_plans/`。
- [ ] 方案列出新增、修改、不修改文件。
- [ ] 方案包含测试/验证方法。
- [ ] 方案包含风险、回退和验证边界。
- [ ] 任务切片可独立验证。
- [ ] 已等待用户明确确认。
