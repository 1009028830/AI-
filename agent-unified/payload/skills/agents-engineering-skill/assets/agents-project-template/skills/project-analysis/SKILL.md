# 项目分析

## 目标

快速建立足够准确的项目上下文，避免凭猜测修改文件。

## 工作流

1. 确认仓库根、适用 AGENTS 和工作区状态，识别已有用户改动：

```bash
git status --short
```

2. 浏览文件结构，优先使用快速搜索工具：

```bash
rg --files
```

3. 搜索任务关键词、入口文件、配置文件和测试文件：

```bash
rg "keyword"
rg --files | rg "(test|spec|config|README|AGENTS|SKILL)"
```

4. 读取 `docs/agent/knowledge-map.md`，只加载与当前任务相关的权威资料。
5. 阅读关键路径。先读入口、接口、调用方和测试，再读实现细节。
6. 用源码、配置或测试确认搜索结论，不把文件名或命中片段当成事实。
7. 汇总：相关模块、关键文件、数据流、现有测试、规则冲突、风险和待确认问题。

## 分析报告格式

```markdown
## 项目分析

### 相关文件
- `path/to/file`: 职责说明

### 当前行为
- [现有逻辑]

### 影响范围
- [可能受影响的模块、配置、测试或数据]

### 风险与待确认
- [需要确认的问题或验证边界]

### 证据
- [文件、符号、配置、命令输出]
```

## 规则

- 不把搜索结果当成最终事实；关键路径必须读取源码或配置确认。
- 优先使用项目已有工具、脚本、测试和文档。
- 发现工作区已有无关改动时，不回退、不整理，只在交付说明中区分自己的改动。
- 分析阶段不改文件，除非用户明确要求。
- 遇到大型或生成文件时先建立结构索引，再按任务读取必要区段。
