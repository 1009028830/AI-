# 统一代码架构与编码规范

版本：v1.3 建议基线  
更新与资料查询日期：2026-10-26  
主要对象：普通 C/C++ 设备软件、Windows/Linux 应用、嵌入式 Linux、STM32 与 ESP32 配套工程；实际采用 ROS 的项目另用对应扩展。

本规范以“驱动—池—应用”总体架构为基础，借鉴 ROS 1/2 的模块组织、接口定义、配置与文档管理思路，方便后续项目统一编写、维护和复用代码。**本次确定的默认方式是参考 ROS 1/2 的工程组织，不以采用 ROS 框架为前提。** 文中的具体目录与职责分工是工程建议；引用的 ROS、SDK 和内核文档约束各自适用环境，不能据此宣称功能安全或标准合规。

本文是可供项目裁剪采用的规范文档，采用规范不自动安装 ROS 或生成可运行工程。项目记录实际平台、语言标准、构建工具和裁剪项；不因目录名称不同批量移动成熟项目代码。正文随 `agents-engineering-skill` 安装，入口只按任务加载相关章节。

## 1. 采用范围与基本原则

### 1.1 默认采用方式与可选扩展

| 方式 | 采用内容 | 适用项目 |
| --- | --- | --- |
| 默认：借鉴 ROS 组织方式 | 模块边界、公共接口、消息契约、配置归属、可替换适配器 | 普通 C/C++、STM32、ESP32、非 ROS 设备服务 |
| 可选：ROS 原生扩展 | package、接口生成、topic/service/action、节点参数、launch、构建与安装机制 | 项目已明确决定采用 ROS 时启用 |

普通项目直接采用通用目录、模块职责和接口合同。模块间按实际需要使用函数、回调、RTOS 队列或现有 IPC；文件夹不自动对应节点、线程或进程。`msg` 表示共享数据契约，`config` 表示受控参数组织，均不预设 ROS 文件格式或运行服务。

ROS 专用段落仅在项目明确采用 ROS 时生效；不因引用 ROS 自动要求安装 ROS/DDS/micro-ROS，创建 `package.xml`，使用 colcon、ament/catkin，或实现 topic/service/action。STM32、ESP-IDF 与内核工程沿用原生构建和运行机制。

对实际采用 ROS 的新工程，优先评估仍受支持的 ROS 2 发行版，按目标操作系统、SDK、第三方包与维护周期选择版本。ROS 1 遗留项目维持必要兼容，迁移单独评估。

ROS Noetic 已于 2025-05-31 结束官方维护；通用规范不硬编码统一 ROS 2 发行版，也不假定不同发行版节点必然互通。[ROS Noetic EOL 官方公告](https://discourse.openrobotics.org/t/ros-noetic-end-of-life-may-31-2025/43160)、[ROS 2 发行版列表](https://github.com/ros2/ros2_documentation/blob/rolling/source/Releases.rst)

### 1.2 项目入口必须说明的事实

在项目已有 README 或架构说明中集中记录以下内容，不重复建立同义文档：

- 运行位置：宿主机、目标板、MCU、容器、内核模块；操作系统与 CPU 架构。
- 语言标准、编译器、实际使用的 SDK/内核及其他框架版本、构建入口、目标配置；使用 ROS 时再记录其版本。
- 实际采用本规范的范围、目录映射与合理例外。
- 核心模块、接口权威来源、启动方式与相关验证入口。
- 涉及真实设备的控制权、执行模式和验收边界。

规则分为：**必须**，用于保持明确边界和正确行为；**建议**，用于新工程默认选择；**按需**，由真实规模、时序或复用需求触发。不能把所有建议转成每次任务必须执行的清单。

## 2. 总体架构与代码职责的对应

### 2.1 保留三大架构边界

| 总体边界 | 主要职责 | 推荐代码归属 |
| --- | --- | --- |
| 应用与控制 | 用例编排、模式、控制状态机、领域算法 | `app/`、`control/`、`algorithm/` |
| 设备服务，原“池层” | 注册、生命周期协调、数据快照、能力查询、命令跟踪、事件汇总 | `services/` |
| 设备与平台适配 | 厂商协议映射、总线收发、操作系统/HAL 接口 | `devices/`、`comm/`、`platform/` |

用户提出的通信、算法、app、控制是代码职责划分，不是必须逐级穿过的四层调用栈。算法通常是供上层调用的独立库；通信处理不应先调用算法再绕到 app。

“池”在本规范中表示设备服务和状态缓存，不等于共享可变全局对象，也不等于内存分配池。实际工程有内存池时使用 `memory_pool` 等明确名称。

### 2.2 典型运行交互

```text
业务入口/UI/远程接口 → app 提交业务意图 → control 检查状态与仲裁
                                             ├→ algorithm 计算
                                             └→ 设备服务执行接口 → devices → comm/platform

设备数据 → devices 解码与规范化 → 设备服务状态快照 → control/app/监控
```

以上是运行时数据与控制方向。源码依赖通过稳定的接口、数据类型和注入的回调表达，不能沿着数据返回方向引入循环包含。

应用可以读取设备服务的公开状态，但普通应用、界面和远程接口不能绕过控制层直接操作执行器。控制意图、执行命令和实际反馈分别表示。需要专用保护或实时路径时明确其所有者、权限、联锁和时限，不将其解释为任意越层访问。

### 2.3 分清代码模块与运行单元

- **模块/库**组织代码职责；构建目标或组件管理依赖与交付；任务、线程和进程承担运行。
- 一个程序可以包含多个模块；小型 MCU 工程也可以在主循环内按明确顺序调用模块。
- 任务、线程与进程按并发、时序和隔离需要选择，不按文件夹数量分配。
- 优先按稳定能力和独立复用边界拆组件；小型单程序允许先在 `src/` 内分模块。

实际采用 ROS 时再区分包、节点、执行器和回调组：一个包可以包含库和多个节点，多个节点可以组合在一个进程中。ROS service 是交互机制，不能直接等同于本规范的 `services/` 代码目录；后者也可通过普通函数接口实现。

ROS 2 的组件机制支持按部署需要选择同进程或独立进程；隔离、通信开销和调试需求分别评估。[ROS 2 Composition 官方文档](https://raw.githubusercontent.com/ros2/ros2_documentation/jazzy/source/Concepts/Intermediate/About-Composition.rst)

### 2.4 硬件隔离的目标与边界

硬件隔离首先要求：上层按设备能力和业务语义编程，厂商型号、寄存器、报文、SDK 与 OS/HAL 差异主要封装在适配层。同一能力合同下可以替换实现；能力、物理行为或时序约束改变时，重新评估受影响的控制策略与验收，不能承诺所有硬件替换都只改驱动。

源码解耦与故障影响隔离分别设计和验证。模块没有相互包含，不代表共享总线、线程、进程、内存或供电故障不会影响其他设备；需要的运行隔离见第 12.4 节。三层架构保持不变，接口、装配和保护约束落实在各层内部。

通过稳定接口连接真实或仿真适配器，使业务核心可以独立于最终设备进行测试，参考 [Alistair Cockburn：Ports & Adapters 原文](https://alistair.cockburn.us/hexagonal-architecture)。本文将这一原则用于现有三层，不要求引入框架或新增运行层。

## 3. 项目目录与可选包布局

### 3.1 默认：普通 C/C++ 工程布局

以下是后续普通 C/C++ 项目的起点，`project` 替换为实际项目名称。目录按需创建，不要求建空目录；成熟工程优先保留已有合理结构。

```text
project/
├── README.md
├── include/project/              # 公共头文件，按模块分子目录
│   └── msg/                      # 无生成器时，共享 C/C++ 数据类型的权威定义
├── src/
│   ├── comm/                     # 通信收发与传输
│   ├── algorithm/                # 算法计算
│   ├── app/                      # 用例与业务编排
│   ├── control/                  # 状态机与控制决策
│   ├── devices/                  # 设备协议与能力适配，按需
│   ├── services/                 # 设备服务与状态快照，按需
│   ├── platform/                 # OS/HAL 后端，按需
│   └── bootstrap/                # 实现选择、对象装配和启动清理，可由薄 main 承担
├── msg/                          # 采用 schema/IDL 生成时的源定义，按需
├── config/                       # 参数默认值、样例及目标配置
├── docs/                         # 架构、接口、协议与使用资料
├── tests/                        # 相关测试和小型 fixtures
├── tools/                        # 项目可复用开发工具，按需
├── third_party/                  # 第三方源码、许可证与来源，按需
└── build/                        # 可再生构建产物
```

`include/src/msg/config/docs` 是文件分类；通信、算法、app、控制是 `src/` 内的职责划分，二者可以同时使用。新增模块先明确归属，再按复用和依赖需求决定是否独立成库，不要求每种职责都是独立工程。

若没有接口生成工具，共享类型由 `include/project/msg/` 管理，根 `msg/` 可以省略；不要手写第二套 `.msg` 或同义结构。采用 schema/IDL 时由根 `msg/` 中的源定义生成类型，生成文件进入构建系统指定目录。模块私有状态仍归模块，不集中到共享消息目录。

STM32CubeMX、ESP-IDF、Linux 内核采用第 17 节的平台映射，借鉴职责划分，保留其工具链要求的目录与构建入口。

### 3.2 按需独立的 C++ 功能模块

```text
project_control/
├── CMakeLists.txt                 # 仅示意 CMake 工程，沿用项目实际构建工具
├── README.md
├── include/project_control/      # 对其他目标公开的接口
│   ├── controller.hpp
│   └── control_types.hpp
├── src/
│   ├── controller.cpp            # 核心控制实现
│   ├── controller_internal.hpp   # 本模块私有声明
│   └── ros/                      # 实际采用 ROS 时才添加
│       ├── control_node.cpp      # 消息、参数和执行器适配
│       └── main.cpp              # 薄入口
├── config/                       # 模块参数样例和默认配置
├── docs/                         # 模块设计与接口解释
└── tests/                        # 测试及 fixtures，沿用项目命名
```

模块内聚与公共接口稳定后再独立拆出；避免同一份实现同时保留在根 `src/` 和模块目录。实际封装为 ROS 包时再添加 `package.xml`、所需 `launch/` 及 ament/catkin 配置，核心库保持可独立构建。

### 3.3 可选参考：实际使用 ROS 2 的多包工作区

本节只用于已明确采用 ROS 的项目，不是通用工程的目录要求。

```text
project_ws/
├── README.md
├── docs/                         # 跨包架构、接口目录、部署与验收
├── src/                          # colcon 工作区源码，不是单个包的实现目录
│   ├── project_interfaces/       # 多包共享的 msg/srv/action 定义
│   │   ├── msg/
│   │   ├── srv/
│   │   ├── action/
│   │   ├── CMakeLists.txt
│   │   └── package.xml
│   ├── project_comm/             # 通信能力及设备协议适配
│   ├── project_algorithm/        # 可独立测试的算法库
│   ├── project_device_services/  # 按需要拆出的设备服务
│   ├── project_control/          # 控制状态机与执行仲裁
│   ├── project_app/              # 业务编排与对外入口
│   └── project_bringup/          # 系统 launch、部署参数和组合选择
├── build/                        # 构建产物，不纳入源码版本控制
├── install/                      # 安装产物，不手工修改
└── log/                          # 工具产生的日志
```

实际工程可以把通信与设备服务合在一个包内。只有模块确实需要独立依赖、发布、替换或复用时才拆包。接口包依赖必要的其他接口包，不依赖 app、控制或设备实现。

纯算法核心即便由 ROS 包导出，也应尽量作为普通 C/C++ 库独立构建；ROS 参数和消息适配放在包装模块。不是每个算法函数都建立独立节点。

ROS 1 使用所选 catkin 工作区与生成布局；不能用 ROS 2 的 ament、rosidl 或 `install/` 约定直接描述所有 ROS 1 工程。

包与接口目录的官方示例见 [Creating custom msg and srv files](https://github.com/ros2/ros2_documentation/blob/rolling/source/ROS-Framework/client-libraries/Working-with-Client-Libraries/Custom-ROS2-Interfaces.rst)。独立接口包是本规范对共享接口的默认建议，不是所有自定义接口都必须单独建包的 ROS 强制要求。

## 4. 头文件摆放与依赖

### 4.1 三类头文件

| 类型 | 放置位置 | 使用边界 |
| --- | --- | --- |
| 公共头文件 | `include/<包或项目>/<模块>/` | 使用者需要的 API、稳定类型和契约 |
| 私有头文件 | 所属模块 `src/` 或组件私有目录 | 只服务实现，不向其他目标导出 |
| 构建时生成头文件 | 构建系统规定的生成/安装目录 | 由 schema、配置或生成器产生，不手工修改 |

头文件自包含：包含它的最小翻译单元不应依赖“先 include 某个别的文件”才能编译。实现文件优先包含自身接口头，再包含其直接依赖；不依赖偶然的传递包含。

普通公共头文件不得定义可变全局对象；函数实现通常放源文件，模板、必要的 `inline`、`constexpr` 等按语言规则保留。避免头文件中的全局 `using namespace`、无关 SDK 类型及整个厂商协议结构泄漏。C 接口需要被 C++ 使用时，按需提供正确的 C linkage 边界。

自有头文件统一 include guard；项目既有 `#pragma once` 约定且目标工具链支持时可以沿用。禁止循环包含、跨包相对路径穿入私有目录、通过聚合 `common.h` 间接引入整个工程。

这些建议参考 C++ Core Guidelines 的 SF 与 I.2 规则；具体 C、内核和厂商源码保持所在工程规则。[C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)

### 4.2 构建边界必须与目录一致

使用目标级 include 与依赖声明：公共接口需要的依赖才传播给使用者，实现依赖保持私有。CMake 的 `PUBLIC/PRIVATE/INTERFACE` 描述使用要求的传播，不是安全隔离机制。避免把全部源码和私有目录加入每个目标的搜索路径。[CMake Buildsystem](https://cmake.org/cmake/help/v4.4/manual/cmake-buildsystem.7.html)

ROS 包还需正确声明 `package.xml` 依赖，并导出/安装公共头文件和库。跨包使用者必须通过导出的目标或接口依赖使用，不从另一个包的 `src/` 直接取文件。

安装 include 目的地、导出目标和使用者搜索路径应采用同一发行版的一致方案，尤其考虑工作区 overlay；纯可执行包不必创建公共头文件目录。[ament_cmake 官方文档](https://github.com/ros2/ros2_documentation/blob/rolling/source/Developer-Tools/Build/Ament-CMake-Documentation.rst)

### 4.3 硬件隔离的依赖约束

- `app/control/algorithm` 的公共接口使用项目数据类型与所需能力接口，不暴露厂商 SDK 结构、HAL 句柄、寄存器地址或原始协议帧；纯算法不依赖设备访问接口。
- 池层依赖设备能力接口，具体适配实现也遵守同一接口。能力接口不反向包含池、app 或厂商实现；具体实现选择集中在第 5.1 节的装配入口。
- 能力接口可按职责放在 `include/<project>/devices/`，池对上层的接口放在 `include/<project>/services/`；目录名称可以适配项目，公共与私有的依赖边界必须可追踪。
- C 可以使用不透明句柄、显式 context 和操作表；C++ 可以使用聚焦的接口类或静态适配。按资源、时序和项目习惯选择，不强制动态分配、虚函数、插件加载或全局服务定位器。
- 禁止把所有厂商 include 路径或 SDK 依赖全局注入每个构建目标。对声明可移植的业务核心提供不包含真实厂商 SDK 的仿真构建，检验传递依赖是否泄漏；目标专有实现保留对应编译验证。

设备型号切换应主要影响适配实现、装配和配置；上层若需要增加厂商型号分支，先检查能力合同是否缺失或设备确实提供了不同的业务能力。库接口约束不能代替进程、内存或硬件隔离。

## 5. 源文件与文件内部顺序

文件按职责命名，如 `can_transport.cpp`、`battery_decoder.cpp`、`power_controller.cpp`、`soc_estimator.cpp`。一个功能可以由多个相关文件实现；不要求“一函数一文件”，也不以固定行数机械拆文件。

建议源文件顺序：

1. 文件用途、关键约束与许可证信息。
2. 自身接口和直接依赖的 include。
3. 命名空间、文件私有常量及私有类型。
4. 必要的私有函数声明。
5. 生命周期和公开接口实现。
6. 私有辅助函数实现；紧邻调用者也可以，保持项目一致。

运行数据按所有权放置：短期值用局部变量；实例状态放对象或显式 context；单文件实现细节才使用文件私有状态。多实例设备不得共用一个隐蔽的可变 singleton。缓冲区、订阅者、线程、文件描述符和锁均指定所有者及销毁顺序。

同一个 `.cpp` 中不同时堆入串口收发、报文解析、控制状态机、算法、UI 和持久化逻辑。`main` 或 `bootstrap` 负责装配、启动与清理，不承载业务决策。

### 5.1 装配入口的责任

装配入口统一读取配置，选择平台后端与设备适配，创建实例并注入依赖；将已满足合同的设备注册到池层，再交给控制和 app 使用。实例以稳定的逻辑设备标识定位，型号、总线地址和实例绑定由配置及适配层管理。

初始化过程区分对象创建、资源初始化、能力核对、必要状态同步与控制启用。业务模块不在构造过程自行查找全局驱动，不因注册成功就自动输出；真实设备的初始化与配置写入仍按目标合同和已有动作授权执行。

关键能力缺失、配置不兼容或初始化失败时，不启用依赖这些能力的控制路径；只在项目明确允许时降级运行，并报告缺失项。退出或替换实例前，先按设备合同处理控制与在途命令，再停止相关回调/任务并释放资源；不得在旧使用者仍引用实例时销毁它。

普通项目优先在启动时确定装配。只有明确需要热插拔、在线换型或动态发现时，才增加对应生命周期、身份核对和重新授权流程。

## 6. 通信、算法、app、控制的职责

| 模块 | 应负责 | 不应负责 |
| --- | --- | --- |
| `comm` 通信 | 收发、连接状态、帧边界、共有传输协议、错误与重连报告 | UI、业务模式决策、SOC 等领域算法 |
| `algorithm` 算法 | 根据显式输入、参数与上下文计算结果 | 直接操作设备、读全局参数服务器、依赖 ROS 节点生命周期 |
| `control` 控制 | 状态机、控制权、联锁、目标约束、调用算法、动作与反馈闭环 | 编解码厂商帧、UI 控件、绕过策略的裸设备写入 |
| `app` 应用 | 用例编排、模式请求、对外 API、业务展示适配 | 自行实现底层保护、直接修改控制器内部状态 |
| `services` 设备服务 | 数据快照、能力查询、注册、命令执行跟踪和事件 | 承担所有业务策略或充当任意读写的全局变量池 |
| `devices` 设备适配 | 厂商寄存器/帧与设备能力之间的映射 | 依赖具体界面、决定系统运行策略 |
| `platform` 平台 | OS/HAL、时钟、同步、设备访问后端 | 领域算法、客户项目业务分支 |

推荐逻辑依赖：`app → control`；`control → algorithm + 设备服务接口`；`app → 状态查询接口`。设备服务通过能力接口使用已装配的设备实现；设备实现通过通信/平台接口完成 I/O。算法库不反向依赖这些模块。

状态更新可经订阅或回调送到上层，但底层只持有稳定接口或注入的回调，不包含 app 的实现头文件。ROS 适配节点将消息转换为核心库输入，再把结果转换回 ROS 接口。

不同控制器对同一执行器的写入必须经过明确的资源所有权或仲裁。手动、自动、远程、维护和保护的优先关系由项目定义，不以“最后写入者获胜”作为默认策略。

### 6.1 按能力定义接口与替换条件

统一的是能力、数据语义与结果含义，不要求只读传感器、电源和电池设备实现同一组控制方法。按实际用例定义最小必需能力，可选能力单独声明；不支持的操作在产生副作用前明确拒绝，不用空实现或假成功凑齐接口。

每类设备能力的合同至少明确：

| 合同内容 | 必须说明 |
| --- | --- |
| 能力与身份 | 稳定逻辑标识、接口版本、必需/可选操作、设备及固件的适用范围 |
| 数据语义 | 类型、单位、正负方向、量程、精度、缺失值与质量含义 |
| 操作条件 | 所需运行模式、控制权、联锁、输入范围与当前可用状态 |
| 时间与资源 | 同步/异步、阻塞上界、更新周期、超时依据、并发/重入和容量约束 |
| 结果与反馈 | 成功的判据、可观察反馈、失败类别及结果未知时的处理 |
| 生命周期 | 初始化、停用、重连、重启、清理，以及在途请求和引用的处置 |

能力查询只表示实现提供什么，不授予控制权，也不保证此刻可以执行。静态额定范围、当前运行限制和业务目标约束分别表达；命令真正执行前重新检查会变化的状态与限制，不直接沿用早先查询结果。

错误至少能区分项目需要处理的“不支持、输入无效/超范围、当前状态不允许、忙、离线、超时、结果未知”等情况；具体枚举、错误码和归属由项目确定。真实与仿真实现遵守相同可观察合同，不能通过静默裁剪目标、改变单位或放宽完成判据实现表面兼容。

### 6.2 池层内部按职责组织

池层对外保持统一入口，内部可按设备或领域组织注册与生命周期、状态快照、命令跟踪和事件管理。它们可以是同一模块内的函数/对象，不要求拆成多个进程或独立框架。

注册表负责身份与实例绑定；快照负责状态发布；命令管理负责路由、关联和结果跟踪；事件管理按需求保留顺序与历史。业务模式、SOC 等算法和控制策略保持在各自模块。池内不得因设备数量增长而形成遍布厂商型号的条件分支，也不向上暴露可任意修改的内部设备对象。

统一访问入口不等于全局可变 singleton。每个状态、队列和实例有明确所有者；耗时 I/O 不持有全局池锁，读状态不隐式触发无界设备访问。

## 7. msg、字段与数据模型

### 7.1 分开三种表示

| 表示 | 例子 | 权威位置 |
| --- | --- | --- |
| 设备线上格式 | CAN ID、位偏移、端序、寄存器、比例、CRC | 当前设备协议/DBC 与对应 codec；来源在协议文档登记 |
| 跨模块/进程接口 | 遥测、控制目标、动作反馈 | 公共头文件中的契约类型，或选定的 schema/IDL；ROS 项目才使用相应接口包 |
| 模块内部模型 | 滤波历史、PID 积分、估计器状态 | 所属核心模块类型或私有实现 |

通信原始数据经过显式校验与转换成为工程量。不得直接发送、接收或持久化 C/C++ 结构体内存来代替协议编解码；结构体填充、端序、对齐、指针和 ABI 不是稳定的线上格式。

`msg` 不收纳所有局部变量。接口定义是跨模块合同；内部模型保持独立，二者映射集中放在边界适配器，不能在多个模块分别维护不同换算。

### 7.2 可选参考：ROS 接口定义

本节只约束实际使用 ROS 的接口。普通工程的共享结构体、枚举和接口契约按第 3.1、4 节维护，不要求新增 ROS 消息生成步骤。

- 多包共享接口优先放独立接口包；仅本包使用的接口按项目规模决定，不强制无限拆包。
- `.msg` 表达数据，`.srv` 表达请求与响应，`.action` 表达目标、结果和反馈。
- 消息名称使用 `PowerModuleState.msg` 这样的 UpperCamelCase；字段使用 `output_voltage_v` 这样的 snake_case；常量使用大写。
- `.msg/.srv/.action` 是人工维护源；生成的 C/C++/Python 类型不另行手写或修改。
- 优先复用语义合适的标准接口；不以字符串、任意 JSON 或大型 `CommonMsg` 包办所有功能。
- 控制相关接口声明数组、字符串和批量操作的容量约束；ROS 2 有界字段可辅助资源估算，但并不自动证明无动态分配或实时性。

ROS 1 与 ROS 2 的字段能力和生成机制有差异，例如 ROS 2 有界字符串/数组不能直接当作 ROS 1 语法。[ROS 接口定义](https://design.ros2.org/articles/legacy_interface_definition.html)

### 7.3 每个字段需要明确什么

按风险填写类型、含义、单位、范围、有效性、来源、更新语义和兼容性。涉及线上协议时再补位宽、字节序、比例、偏移、缺失值及保留值；不是每个内部变量都制作字段表。

ROS 接口遵循对应标准消息的单位和坐标约定。自定义接口默认采用一致的工程单位；确需定点数或特殊单位时在名称和注释中标明并在适配层换算。空间数据说明 `frame_id`，不要用它代替设备编号。[REP-103](https://github.com/ros-infrastructure/rep/blob/master/rep-0103.rst)

在 ROS 工程中，电池消息可先评估 `sensor_msgs/BatteryState`：其电压单位为 V，电流单位为 A 且放电为负，`percentage` 为 0–1；部分未测量值用 NaN 表示。上游设备若采用相反电流方向或 0–100 SOC，必须转换。不能只因字段名字相同就认为语义兼容；普通项目按自身协议明确方向和单位，不强制沿用该消息类型。[BatteryState 原始定义](https://raw.githubusercontent.com/ros2/common_interfaces/rolling/sensor_msgs/msg/BatteryState.msg)

下面是自定义电源模块状态的 ROS 2 接口形态示例，容量和字段须按实际设备调整；不是已生成或联调的接口：

```text
# PowerModuleState.msg；quality=VALID 时，两项工程量都必须有效且为有限数。
uint8 UNKNOWN=0
uint8 VALID=1
uint8 STALE=2
uint8 INVALID=3
std_msgs/Header header
bool source_stamp_valid
string<=64 device_id
uint64 sample_sequence
uint8 quality
float32 output_voltage_v
float32 output_current_a
```

示例约定：`header.stamp` 为映射到所选 ROS 时钟的源采样时间；无法确定时 `source_stamp_valid=false`，不能把接收时间伪装成源采样时间。电流正方向定义为电源模块向外输出；序号仅在当前采集会话内比较。没有空间参考时按接口合同处理空 `frame_id`。需要逐字段质量或跨重启去重时显式扩展有效性和会话标识。

### 7.4 演进与兼容

变更字段名称、类型、单位、语义、数组长度和接口定义时，检查所有调用方、编解码器及已有持久化数据；发布二进制库时还需评估 ABI。ROS 工程另检查发布者、订阅者、桥接器及历史录包，不能假定“只加一个字段”在所有 ROS 版本、RMW 和录包工具中均兼容，也不能因为增加一个 `version` 字段就声称解决类型兼容。

不兼容变化采用新接口/版本化端点和有期限的适配迁移；源 schema、生成器版本和消费者更新关系可追溯。使用 Protobuf 的工程另遵循其字段编号与保留规则，不能把这些规则混当 ROS 消息兼容机制。[Protobuf Best Practices](https://protobuf.dev/best-practices/dos-donts/)

## 8. 模块交互方式与可选 ROS 映射

### 8.1 默认采用项目需要的交互方式

| 交互需要 | 普通工程可选实现 | 必须说明 |
| --- | --- | --- |
| 同步计算与短时查询 | 普通函数、对象接口 | 输入输出、错误、执行上下文和阻塞上界 |
| 状态更新与事件通知 | 回调、任务队列或现有事件机制 | 数据所有权、更新频率、容量、过期与溢出处理 |
| 持续执行的任务 | 显式状态机、任务接口与结果查询/通知 | 请求标识、进度、取消、超时和最终设备反馈 |

同进程模块优先使用满足需要的简单接口；跨线程、跨进程或跨设备时再选择对应传递机制。不为了模仿 ROS 自建通用消息总线、参数服务器或调度框架。提交成功、已受理与实际完成分别表达；调用方超时不代表设备已经停止。

### 8.2 通用命令与反馈合同

控制接口必须区分本地提交、设备受理与实际完成。请求与反馈至少能关联到目标设备、当前会话及请求；项目声明哪个环节受理了请求，以及完成判据是设备确认、经核实的状态反馈还是其他证据。

下表是需要表达的语义，不强制采用这些英文枚举或要求每条命令经过所有阶段：

| 语义 | 含义与约束 |
| --- | --- |
| 拒绝 `REJECTED` | 在交付执行前因能力、参数、状态或容量等原因拒绝；不得用于表示已经发出但结果不明 |
| 已受理 `ACCEPTED` | 指定环节接受处理，需说明是本地队列还是设备受理；不等于执行成功 |
| 执行中 `RUNNING` | 有执行中的依据；无可用反馈时不伪造进度 |
| 已完成 `SUCCEEDED` | 达到合同规定的完成判据；写入驱动缓冲区或仅收到通用 ACK 不自动满足 |
| 已失败 `FAILED` | 有确认的失败依据；报告已知的部分完成和剩余影响 |
| 已取消 `CANCELLED` | 按合同完成取消或停止，并给出可用证据；收到取消请求不代表已经停机 |
| 结果未知 `UNKNOWN` | 超时、断连等导致无法确认结果；这是观察状态，不应伪装成设备终态 |

明确请求有效期、在途容量、并发目标、抢占/合并规则与控制权归属。队列中已过期或控制权已失效的命令不得继续派发；持续设定值可在合同允许时合并，离散动作不能默认按“最后一条覆盖”处理。

协议支持请求标识时核对设备、会话和响应关联；不支持时通过受限并发、协议时序和状态核对建立可证明的关联。接收时间或一次相同目标值的读回，不必然证明本次动作由该请求完成。

调用方超时不表示设备未执行。结果未知时先按合同查询、对账或进入受控状态；只有操作可安全重试或具有有效幂等/去重保证时才有限重试。本地请求编号本身不能提供设备端去重或跨重启的“恰好执行一次”。

设备重启或会话变化后，旧在途请求单独结算或标为未知，旧控制命令默认不重放。迟到反馈不得完成新会话中的请求；如允许据其修正旧请求的观察结果，应保留证据和变更记录，不触发重复动作。不能可靠识别重启/关联时，记录这一限制并采用保守恢复流程。

### 8.3 可选参考：实际采用 ROS 时的机制选择

| 机制 | 优先场景 | 必须补充的工程语义 |
| --- | --- | --- |
| topic | 遥测、设备状态、诊断、连续设定值流 | 发布者权威性、频率、QoS、过期判断、失联策略 |
| service | 短时查询、快速且有界的请求/响应 | 超时、错误、幂等性；响应到底表示受理还是完成 |
| action | 持续执行、需要进度和最终结果的任务 | 并发目标策略、取消/抢占行为、终态与设备反馈 |

service 客户端可以异步调用；请求/响应模型不等于必须阻塞线程。长过程不能一直占用普通 service 回调等待设备；topic 发布成功、service 返回、action 目标受理均不自动等于物理动作完成。[ROS 2 接口文档](https://raw.githubusercontent.com/ros2/ros2_documentation/jazzy/source/Concepts/Basic/Interfaces-Topics-Services-Actions.rst)

action 取消是请求，服务器可以拒绝；接受后还需完成规定的安全停止或清理，再报告相应终态。客户端超时或掉线不等于远端已取消；设备动作成功、失败、未知要有可观测依据。去重和跨重启恢复若有需求，单独定义，不能认为 ROS UUID 自带持久化的“恰好执行一次”。[ROS 2 Actions 设计](https://design.ros2.org/articles/actions.html)

连续控制设定值可以使用 topic，但必须定义控制权、命令有效期、超时后的项目安全行为。真正的紧急保护不依赖尚未证明延迟上界的普通网络回调。

### 8.4 可选参考：ROS 命名、QoS 与可观测性

- 多设备/多实例优先使用 namespace、相对名称与 remap，不将机器人或设备绝对路径散落在源码中。
- 接口目录登记名称、类型、发布/消费方、频率、单位、QoS 和失联处理。
- 遥测、状态快照、离散故障事件和命令分别设计队列与可靠性；不要所有 topic 都使用默认 depth 或最大可靠性。
- 检查发布和订阅 QoS 是否兼容；`reliable` 不代表业务一定完成、永不丢历史或具有硬实时保证。
- `transient_local` 可服务晚加入者的状态获取；执行命令默认避免历史重放，任何例外必须有过期、控制权和重放防护。
- deadline、lifespan、liveliness 是通信策略/监测信息，设备故障与保护动作仍由应用合同决定。

依据：[ROS 2 Jazzy QoS 官方源码](https://raw.githubusercontent.com/ros2/ros2_documentation/jazzy/source/Concepts/Intermediate/About-Quality-of-Service-Settings.rst)。其他发行版与 RMW 组合需按实际环境核对。

## 9. 数据池、缓存和时间

每类状态有明确权威来源和更新者；读者通过快照或消息读取，不跨模块持有可变内部指针。单写者也不能自动消除多线程读写的数据竞争，仍需合法的同步或快照发布机制。

数据快照至少能表达值、设备来源、更新序号/版本、时间含义和质量。源采样时间与本机接收时间分开；跨设备数据用于同一计算时规定可接受的时间偏差。设备离线、重启或重连后旧快照失效，不用默认零值冒充有效数据。OPC UA 的数值、状态和时间表达可作参考，但本规范不要求引入 OPC UA。[DataValue](https://reference.opcfoundation.org/specs/OPC-10000-4/7.11)

运行超时优先基于目标环境的单调时钟；ROS 消息时间按所选 ROS 时钟语义表达。启用模拟时间时处理暂停、回退和跳变；不同机器的单调时间不能直接相减，仿真时间也不能替代真实保护计时。[ROS Clock and Time](https://design.ros2.org/articles/clock_and_time.html)

缓存不必集中在一个“全局池节点”：按设备或领域维护所需快照，跨节点通过明确接口交换。展示可取最新值；故障事件与命令结果按需求保留顺序、确认和容量耗尽策略。

### 9.1 状态新鲜度与恢复规则

- 项目按每类数据定义新鲜度依据、过期条件与失效后的消费者行为；阈值来自采集周期、通信预算和控制需求，不在通用规范中固定。
- 本机单调接收时间可用于本机超时判断，源采样时间用于表达采集时刻；仅收到报文不能证明其中数据是新采样，设备缓存/重发语义也要纳入判断。
- 采集周期不同的字段需要独立质量或更新时间；多字段快照声明一致性边界，不能把不同采样周期的数据拼成未经说明的“同一时刻”。
- 无效或过期数据可保留最后已知值供诊断，但必须显式标记；控制消费方按项目合同拒绝或进入规定策略，不把它当有效输入继续使用。
- 离线、重启、设备身份改变或重连后重新建立身份、会话和必要状态。仅链路恢复不等于状态可信，更不等于恢复原控制输出；在满足恢复条件前保持相应控制限制。
- 状态快照与离散事件分别存储和传递；最新值覆盖不能悄悄吞掉必要的故障转换或命令结果。

## 10. 配置文件与全局参数

### 10.1 文件分类与运行时所有权

| 内容 | 建议位置/方式 | 约束 |
| --- | --- | --- |
| 编译选项、目标能力 | CMake、Kconfig、sdkconfig、工具链文件 | 随构建版本固定，不冒充运行时热参数 |
| 模块运行参数 | 项目或模块 `config/`；由启动入口加载与分发 | 声明类型、单位、默认值、范围、读写权限和生效时机 |
| 板卡/设备配置 | 项目设备配置或平台配置 | 型号、通道、地址、协议版本明确 |
| 标定与保护参数 | 受控配置和版本化标定产物 | 来源、硬件版本、适用范围、变更权限与回退可追溯 |
| 运行状态 | 模块对象、状态机或数据快照 | 不混入参数文件作为任意持久化变量 |
| 凭据与账号授权 | 目标环境密钥机制 | 不进入仓库、参数样例、录包或普通参数服务 |

“全局配置”表示统一组织与发布，不表示全局共享可变变量。默认由启动入口读取并校验配置，再通过结构体、对象或明确接口交给各模块；模块对自身状态负责。需要跨模块或进程一致的参数，明确来源、配置修订号与协调机制；不能认为多次独立设置构成跨模块事务。

实际采用 ROS 时，分别处理 ROS 1 参数服务器与 ROS 2 节点拥有的参数模型。ROS 2 节点应声明并校验参数；多个节点都使用的值可以由同一配置入口分发，但每个节点对自身生效状态负责。参数变更不默认持久化到原 YAML，需持久化时单独定义。单节点成组原子设置与跨节点配置一致性是不同问题。[ROS 2 参数迁移官方文档](https://github.com/ros2/ros2_documentation/blob/rolling/source/Migration-and-Upgrades/Migrating-from-ROS1/Migrating-Parameters.rst)

### 10.2 配置组织

项目或模块 `config/` 保存默认值/样例及目标配置；文件格式沿用项目实际工具，小型 MCU 可以使用受控的编译期配置结构，无需为规范引入 YAML 解析器。可以按“明确默认值 → 设备/场景配置 → 受控部署覆盖”组织，但实际加载顺序与重复项优先级必须由启动入口显式实现、记录和测试，不能把这当成所有框架固有规则。

仅供 ROS 2 工程参考：包内配置保存模块默认值，bringup 保存产品和部署组合。其参数文件示意如下，数值只用于说明结构，不作为设备控制默认值，也不是普通工程必须采用的配置格式：

```yaml
/demo/power_monitor:
  ros__parameters:
    publish_rate_hz: 5.0
    device_id: "demo_power_01"
    expected_frame: ""
```

使用节点 namespace 和通配规则时避免意外覆盖其他实例。配置读取不要依赖当前工作目录或开发机绝对路径；ROS 包资源通过安装后的包资源定位，非 ROS 程序由显式参数/约定的部署位置定位。

### 10.3 参数变更规则

- 配置加载先验证，再整体发布给模块；关联参数检查组合约束，拒绝部分生效的破坏性中间状态。
- 区分只读、重启生效、停机生效和可在线修改参数；不为方便将全部参数设为热更新。
- 在线更新采用不可变配置快照或受控同步，不能一边计算一边修改同一配置结构。
- 校验阶段不执行设备动作；变更被接受后，按可追溯的生效流程执行必要副作用并报告失败。
- 参数服务成功与硬件配置已成功生效分别记录；跨节点/设备生效不能假定具有原子性。
- 非法、缺失、旧版配置按合同拒绝或使用已验证的降级方案；保护参数不得静默回退为猜测值。

## 11. 控制、算法与设备执行

控制层明确状态、事件、合法转换、进入/退出动作、取消策略、超时和恢复条件。控制权和状态检查集中在规定入口，执行设备的底层适配不自行决定业务授权。

算法通过输入和显式 context 接收所需状态、时间步长和参数；必要的历史状态归算法实例所有。测试可以使用确定的输入序列与时钟。规定输入范围、饱和/溢出、非有限数、数据缺失及数值精度；结果是否允许驱动设备由控制逻辑判断。

需要周期闭环的项目可以参考 `read → update → write` 的结构，并核算完整周期的执行时间、抖动和阻塞。ros2_control 提供这种组织方式，但采用它不自动证明项目满足硬实时或功能安全。[ros2_control Controller Manager](https://control.ros.org/rolling/doc/ros2_control/controller_manager/doc/userdoc.html)

ACDC/DCDC 若是外部设备，厂商协议放设备适配；若是本机功率控制，采样、算法、PWM 和保护按实际 MCU 时序设计。BMS 的 SOC/SOH 算法、业务充放电策略、硬件保护和远端 BMS 协议分别标明归属，不能全部称为“电池驱动”。

真实设备动作的授权、联锁、安全状态、阈值和时限来自项目与硬件资料。保护执行路径按风险前置设计；数据展示或普通告警汇总路径不能充当未经验证的保护链。

### 11.1 控制权与保护责任

项目按实际存在的机制分配责任，不能从目录位置推定保护能力：

| 责任范围 | 负责内容 | 必须明确的边界 |
| --- | --- | --- |
| app 与策略 | 业务目标、运行模式请求、调度 | 不直接恢复保护、不绕过控制入口写执行器 |
| control 与联锁 | 控制权仲裁、模式转换、可执行条件与目标约束 | 每个执行器明确普通命令的最终执行入口及检查责任 |
| 本机快速控制/保护（如有） | 满足项目时限的采样、闭环或软件保护 | 独立规定执行上下文和时间预算，不依赖普通池队列才触发必要保护 |
| 硬件保护（如有） | 由实际电路和器件实现的保护动作 | 来源、触发、反馈、失效与复位条件由硬件资料和验证确定 |

保护生效时，明确谁禁止后续普通命令、取消或冻结在途操作、发布状态，以及允许谁恢复。相关失效事件与执行入口之间应有可靠的联锁，不能只在界面隐藏按钮或寄希望于上层及时轮询。

保护复位、链路恢复和控制重新使能是不同动作。恢复按合同重新核对设备状态、控制权与前置条件，不因清除告警就自动重放历史目标。安全状态、优先关系、动作顺序和时限均以当前项目为准；通用规范不指定保护阈值或替代安全评估。

## 12. 并发、生命周期与资源

### 12.1 通用运行模型

每个模块说明由主循环、任务、线程还是回调驱动，谁持有状态、何时更新、是否允许阻塞和重入。调用与数据交接方式由实际平台选择；算法或业务目录不自动要求独立线程。状态所有权与同步规则独立于采用哪种框架。

**以下仅在实际使用 ROS 时适用：**

节点说明执行器选择、回调组、共享状态所有权和阻塞行为。MultiThreadedExecutor 不自动使代码线程安全；默认互斥回调组也不能保护其他回调组、工作线程或外部代码。

回调内同步等待服务或 action 结果时，检查其完成回调能否获得执行机会；优先采用有超时的异步流程，避免同一互斥组内等待自身完成条件。保留回调组及相关实体所需生命周期。[ROS 2 Callback Groups](https://raw.githubusercontent.com/ros2/ros2_documentation/jazzy/source/How-To-Guides/Using-callback-groups.rst)

### 12.2 设备生命周期

按需要明确初始化、已配置、可用、激活、故障、停止与清理状态。ROS lifecycle 可提供结构，但不能假定设置为 inactive 就自动停止所有自建线程、订阅或硬件输出；每种副作用由实现控制。[Managed Nodes 设计](https://design.ros2.org/articles/node_lifecycle.html)

失败回收、关闭、取消和重启要覆盖定时器、回调、工作线程、I/O、DMA 和缓冲区仍在使用的情况。退出前先阻止新操作，再同步/停止在途使用，最后释放资源；具体硬件停机顺序以设备合同为准。

### 12.3 MCU 与内核边界

ISR 只执行必要、有界且上下文允许的工作；不能从 ISR 等待普通线程、执行阻塞服务或获取不允许的锁。DMA 缓冲区说明区域、对齐、生命周期和缓存一致性。`volatile` 不代替互斥、原子操作、内存排序或跨核同步。[Linux volatile 说明](https://docs.kernel.org/process/volatile-considered-harmful.html)

实时路径为分配、锁、日志、I/O 和队列制定资源与时间上界；发生队列满、执行超时或内存耗尽时有明确反馈。避免默认引入无界队列、无限重试和无限等待。

### 12.4 故障影响范围与资源预算

在项目架构说明中标明设备共享的总线、锁、执行线程/任务、进程、内存和供电资源，以及相关故障会影响谁。软件调用边界不能消除总线或供电的共同故障；业务要求独立运行时，需相应的运行或硬件设计支撑。

对可能阻塞或失败的路径规定 I/O 超时、单次执行时间、队列容量和重试预算。按实际时序选择非阻塞 I/O、任务调度或受控工作线程，不要求每个设备一个线程。共享总线声明访问仲裁、优先级与占用预算，单设备重试不能无限占据资源。

队列满时按数据类别处理：可覆盖的状态采用合同允许的合并；故障事件和离散命令明确拒绝、反馈、持久化或升级处理规则，不能静默丢弃。耗时 I/O、日志和外部回调不得持有保护其他设备所需的全局锁。

需要崩溃隔离时评估进程/内存保护及恢复机制；将驱动放到另一线程不能隔离内存破坏。确需独立安全或故障域时，以目标系统证据说明能力，不把源码分层或队列拆分当作已经实现故障隔离。

恢复流程遵循第 8.2、9.1 和 11.1 节的命令、状态及保护约定；恢复通信不能绕过重新确认状态与控制条件的步骤。

## 13. 语言、命名与编码要求

- 新代码遵循所在目标的语言标准、格式工具和命名习惯；C 与 C++ 不机械套同一套类型与资源管理方式。
- 自有文件、目录和普通标识符使用清晰的英文名称；注释与文档默认简体中文。ROS 接口命名遵循第 7 节；第三方、生成代码和内核保持上游风格。
- C 公共符号使用项目/模块前缀；C++ 使用命名空间。避免含义模糊的 `data1`、`manager2`、大范围 `utils` 和未经约定的缩写。
- C 通过明确所有权、返回状态和清理路径管理资源；C++ 优先使用 RAII 和合适的值类型/智能指针，避免默认共享所有权。
- 公共 API 说明输入输出、所有权、线程/ISR 上下文、阻塞、超时、错误、有效期和重入性。只给 `bool` 却无法区分重要失败原因时，应提供稳定错误类型。
- 检查外部长度、范围、编码和数值转换；特别关注带符号/无符号混算、溢出、越界、未对齐访问和未定义行为。
- 用具名常量表达协议固定值与单位转换，用配置表达真正可变的工程参数；不是所有常量都搬进 YAML。
- 字节缓冲区与长度一起传递；借用指针或视图说明生命周期。跨异步边界不保存指向临时对象或复用接收缓冲区的引用。
- 宏不隐藏控制流和重复求值；有类型的常量或函数可表达时优先使用。
- 函数按职责组织并控制嵌套；注释解释契约、原因和约束，不逐句翻译代码。
- 普通 C/C++ 公开接口与关键模块采用项目既有 Doxygen 约定；Linux 内核使用 kernel-doc。按第 13.1–13.5 节选择格式与详细程度，不强制每个简单 getter 堆同样模板。修改行为同步更新相关注释。
- 日志包含必要的设备/节点、请求、状态和错误上下文，限频并脱敏；不记录凭据，不在实时回路中进行不可控格式化或阻塞输出。
- namespace、设备编号与网络发现用于组织和定位，不能充当控制授权；远程控制入口在可信边界认证、校验权限并记录必要审计，通信安全与网络隔离按部署风险配置。
- 所有 I/O 错误按边界处理；重试有次数/时间预算，并考虑部分完成与幂等性。不能通过捕获所有异常后继续运行掩盖故障。

C++ Core Guidelines 是可裁剪工程指南；Linux 内核、ESP-IDF 与芯片 SDK 的适用规则另见平台映射。没有指定合同与标准版本时，不宣称统一满足 MISRA、AUTOSAR 或功能安全要求。

### 13.1 注释分类与权威位置

注释用于表达接口合同、设计原因和使用限制。普通 C/C++ 新代码默认使用 `/** ... */` 文档块；已有 `///`、`/*! ... */` 等约定且工具支持时沿用，不仅为统一外观批量改写旧代码。

| 位置 | 推荐方式 | 需要表达的内容 |
| --- | --- | --- |
| 文件或模块入口 | 简短 `@file`、`@brief`，复杂关系链接模块 README | 职责、所属边界、关键约束；保留实际许可证和版权声明 |
| 普通 C/C++ 公共接口 | 公共声明处的 Doxygen 文档块 | 输入输出、错误、所有权、生命周期、执行上下文、阻塞/超时及副作用 |
| 私有函数 | 实现附近的简短说明，复杂或高风险时补充契约 | 非显然用途、前提、状态变化和限制；简单直观函数可省略 |
| 字段、枚举与常量 | 简短 `///<` 或 `/**< ... */`，内容较长时前置文档块 | 单位、方向、范围、有效性、位含义和特殊值 |
| 内部实现 | 普通 `//` 或 `/* ... */` | 设计理由、不变量、并发/硬件限制、必要算法依据 |
| Linux 内核接口 | kernel-doc，位置遵循子系统约定 | 参数、调用上下文、锁/睡眠条件和返回语义 |

公共接口说明集中维护一份。源文件补充实现原因，避免在 `.h` 与 `.c/.cpp` 复制两份长文档；模板、内联及仅实现可见的接口按实际位置维护。领域字段以接口定义为权威，其他文档链接说明，不重复维护易失配的字段表。

自有注释正文默认简体中文，标识符与协议名使用惯用英文；上游代码及对外贡献遵循其语言约定。自有新代码不强制每个函数填写作者、修改日期和历史流水账，版本历史由 Git 管理；第三方版权、许可证和原有必要说明不得据此删除。

依据：[Doxygen 文档块](https://www.doxygen.nl/manual/docblocks.html)、[ESP-IDF Documenting Code](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/contribute/documenting-code.html)、[STM32 HAL UART 官方注释示例](https://github.com/STMicroelectronics/stm32f4xx-hal-driver/blob/master/Inc/stm32f4xx_hal_uart.h)。这些资料说明各自项目实践，不构成全行业注释使用率排名。

### 13.2 公共接口的 Doxygen 约定

- `@brief` 用一句话说明可观察的功能，不只复述函数名。
- `@param[in]`、`@param[out]`、`@param[in,out]` 对应真实读写语义；说明长度/容量、空指针规则、单位、所有权、有效期和失败后的输出状态等必要信息，不机械重复类型。
- `@return` 说明返回值总体语义；需要区分具体状态时用 `@retval`。无参数或无返回值的函数不填写空 `@param`、`@return`。
- `@pre`、`@post`、`@note`、`@warning` 按实际需要使用；前提条件注释不能替代边界输入校验、控制授权或安全联锁。
- 并发、ISR、锁、资源所有权等可使用 `@par 执行上下文` 等小节。未配置别名时，不自创 `@threadsafe`、`@isr` 等标签并假定工具认识。
- 异步接口必须说明“受理”和“完成”的区别、参数是否复制、回调发生位置、取消/超时与对象销毁的关系；语义与第 8.2 节一致。

以下为池层接口的注释格式示意，类型、错误码及行为由具体项目定义；没有对应实现时不能据此宣称具有所述线程或时序能力：

```c
/**
 * @brief 复制指定设备的最新缓存状态快照。
 *
 * @param[in] service 已初始化的设备服务；调用期间不得销毁。
 * @param[out] out_state 接收快照，不能为空；失败时保持原值。
 *
 * @retval DEVICE_OK 成功取得快照。
 * @retval DEVICE_ERR_ARGUMENT 参数无效。
 * @retval DEVICE_ERR_NO_DATA 尚未取得该设备的数据。
 *
 * @par 执行上下文
 * 仅供普通任务调用；内部获取互斥锁，可能等待，不允许在 ISR 中调用。
 *
 * @note 本函数读取缓存，不触发硬件 I/O。
 *       返回成功只表示取得快照，数据能否用于控制仍需检查质量与时间。
 */
device_status_t device_get_snapshot(
    device_service_t *service,
    device_snapshot_t *out_state);
```

有锁或阻塞的真实接口还需在项目合同中给出等待策略与适用预算；注释不得凭空保证“线程安全”“无阻塞”或“固定时间完成”。这些属性必须与调用上下文、实现和验证证据相符。[Doxygen 命令说明](https://www.doxygen.nl/manual/commands.html)

### 13.3 字段、实现与硬件相关注释

字段说明优先补充类型和名称无法表达的语义。例如下面两行为结构体成员片段，正方向只表示本示例约定，实际值按项目接口合同确定：

```c
float output_voltage_v; /**< 输出端电压，V；仅在该字段质量有效时使用。 */
float output_current_a; /**< 输出端电流，A；本示例约定向外输出为正。 */
```

实现注释解释为何保留某个分支、顺序或限制，例如“旧会话反馈只用于核对旧请求，不能完成当前会话中的命令”。避免给每次赋值、循环或普通函数调用配逐句翻译；复杂算法可说明推导、误差、边界与来源，不用注释掩盖混乱的实现。

涉及寄存器副作用、读清/写清、时序等待、DMA 缓冲区、缓存一致性、锁与中断限制时，记录关键原因，必要时链接设备型号、手册版本、章节或勘误编号。厂商差异的详细原因留在适配层，上层注释维护稳定能力语义。

可调阈值的来源与含义链接到配置/标定合同，避免在注释里维护一份可能失效的数值。临时绕行说明触发条件、影响与可移除条件；待办引用真实的问题记录，不虚构编号或留下无内容的模板标签。删除旧代码依靠版本控制，不长期保留大块注释掉的实现。

### 13.4 Linux 内核的 kernel-doc 例外

内核 API 使用 kernel-doc，不能把 Doxygen 的 `@param`、`@retval` 直接替换进去。典型形式为函数名摘要、`@参数名:`、`Context:` 和 `Return:`；实际导出接口、私有函数和类型的覆盖范围遵循目标内核与子系统要求。

以下仅示意 kernel-doc 语法；英文示例适用于上游风格，真实行为必须核对实现：

```c
/**
 * example_read_status() - Read the cached device status
 * @dev: Initialized device instance
 * @status: Output buffer; unchanged on failure
 *
 * Context: Process context. May sleep while acquiring the instance mutex.
 * Return: 0 on success, or a negative error code on failure.
 */
```

内核文档块紧邻其描述的函数或类型，维护者约定优先。普通 Linux 用户态程序仍可使用 Doxygen；运行在 Linux 上不等于属于内核代码。[Writing kernel-doc comments](https://docs.kernel.org/doc-guide/kernel-doc.html)、[Linux 注释原则](https://docs.kernel.org/process/coding-style.html#commenting)

### 13.5 注释验证与停止条件

修改接口时同步核对参数名、返回语义、数据所有权、单位、上下文和链接；必要时更新受影响的文档生成。纯文字调整只检查相关差异与引用，不触发业务全量回归。

项目已有 Doxygen 或 kernel-doc 检查时复用相关入口，按目标版本检查新增文档块；不因通用规范自动安装文档工具或对所有私有函数启用文档覆盖率门禁。语法工具通过只说明对应格式检查通过，不能证明注释描述的线程安全、时序或硬件能力。

可执行示例在适用环境中验证；声明片段、字段片段和纯注释示例注明用途，不当作可直接运行的完整工程。一次相关检查及集中审查通过后停止，后续仅在受影响的代码或注释变化时增量复核。

## 15. 构建、依赖与跨平台

- 固定能影响交付的源码、工具链、ROS/SDK、生成器、配置和依赖版本；明确第三方来源与许可证。
- 源码与构建输出分离；ROS 生成接口和普通构建生成文件进入工具管理目录。CubeMX 生成的工程源码属于不同情况，见第 17 节。
- 按交付方式安装公共头文件、库以及运行需要的配置；ROS 项目另包含所需 `launch` 等资源。从安装产物启动仍应能定位配置，不依赖源码树残留。
- 检查声明依赖是否足够，避免因为开发机已安装额外包或源目录进入搜索路径而偶然构建成功。
- Windows/Linux 共用业务与算法源码，平台后端分别构建和验证。路径由参数、资源定位或部署配置取得，不硬编码个人目录。
- 脚本、Python 包、前端等遵循相应工具链原生布局；不人为添加没有意义的 C/C++ `include/` 或节点层。
- 不因本规范自动引入 ROS、DDS、数据库、消息队列或其他运行依赖；真实需求与项目授权决定采用。

## 16. 测试、审查与停止条件

### 16.1 日常顺序

明确接口与验收条件 → 最小贯穿实现 → 编译/基础检查 → 相关功能验证 → 一轮集中审查。

设计阶段需要的安全分析和危险操作执行前核对仍然前置。审查发现问题后，只重跑受影响检查并复核修复差异；无新增变化和风险证据时停止。编译成功、录包回放成功或测试通过都只说明实际覆盖范围。

### 16.2 按改动选择验证

| 改动 | 优先验证 | 何时扩大 |
| --- | --- | --- |
| 纯算法 | 主路径、边界、数值异常、确定性与误差范围 | 目标数值实现、性能或编译选项改变 |
| msg/接口 | 使用方编译、字段语义、相关编解码与历史数据兼容；采用生成器/桥接时再验证对应步骤 | 影响多模块、多设备或多版本部署 |
| 通信/设备适配 | 正常帧、截断、非法长度/值、超时、断连、部分收发 | 更换总线、驱动或真实设备 |
| 控制 | 状态转换、冲突、失效数据、命令超时、取消与反馈 | 真实执行器、保护时序或运行模式改变 |
| 参数 | 类型/范围/组合校验、覆盖顺序、失败不部分生效 | 跨节点协调、硬件写入或标定变化 |
| ROS 节点/组合 | 启停、namespace、QoS、执行器/回调、资源定位 | 进程组合、RMW、网络或操作系统改变 |
| 文档/规则 | 结构、引用、示例边界与冲突 | 文档同时改变构建、生成或执行行为 |

相关模块构建、接口检查、交付资源和功能验证对应当前交付版本；实际使用接口生成器或 ROS 包时，再执行对应生成与包构建。确实使用模拟器或 rosbag 时，说明其与目标设备的差异；不能用回放代替真实 I/O、时序或安全联锁验证。

验证命令记录在项目已有入口。日常选择相关模块及受影响依赖；跨模块、发布或项目门禁要求时才运行更大回归。改接口时包含受影响的使用方，不能只构建接口定义自身。

### 16.3 新模块的最小完成条件

1. 目录、职责、公共接口与状态所有者清楚。
2. 参数与消息有必要的单位、有效性和错误语义。
3. 没有新增循环依赖或绕过控制入口的设备写入。
4. 正常路径和本次涉及的关键失败路径有验证证据。
5. 相关构建通过，公开接口与运行资源可被正确使用。
6. 一轮集中审查完成，未覆盖目标环境和剩余限制已记录。

小型局部修改直接复用已有模块合同和证据，不为每次编辑重建整套文档、测试矩阵或审查流程。

### 16.4 硬件隔离的验收

新增能力接口、接入/替换设备或调整运行边界时，按影响选择以下验收；它们不是每次修改必须重跑的整套门禁：

| 验收目标 | 方法 | 通过所证明的范围 |
| --- | --- | --- |
| 依赖隔离 | 在不提供真实厂商 SDK 的配置中构建可移植核心和仿真适配 | 当前构建未依赖真实厂商 SDK；不证明目标硬件正确 |
| 实现替换 | 同一能力合同使用两个适配实现，复用业务场景，仅改变装配/配置 | 已覆盖场景下的接口替换；不证明所有硬件等价 |
| 能力与异常 | 覆盖必需能力缺失、可选能力不支持、超范围、模式不允许和忙 | 当前合同中的拒绝与错误语义成立 |
| 状态与会话 | 模拟过期、断连、重启、重连、旧反馈和跨字段不一致 | 已覆盖场景的状态有效性及命令关联正确 |
| 命令与保护 | 验证超时后未知、取消未完成、控制权切换、保护禁止与恢复 | 对应模型或目标环境中的执行约束；记录验证环境 |
| 运行隔离 | 在仿真或已授权目标环境中制造阻塞、队列满和有限重试 | 指定故障条件下，对其他任务的影响符合已声明预算 |
| 生命周期 | 初始化中途失败、停止时仍有在途请求、实例更换 | 相关资源与请求按合同回收，旧实例不再被使用 |

仿真实现可以覆盖正常与可控失败路径；真实适配另需对应协议及目标验证，不能由仿真结果代替。任务初次采用这些验收后，记录命令、版本、场景、结果和未覆盖项，后续只在相关输入或环境改变时增量复核。

## 17. 平台映射与裁剪

| 环境 | 推荐采用 | 必须保留的边界 |
| --- | --- | --- |
| 普通 Linux/Windows C/C++ | 默认采用第 3.1 节布局与通用模块合同 | POSIX/Windows 资源与 I/O 各自适配；借鉴 ROS 不引入其运行依赖 |
| STM32CubeMX | 自有 app/control/algorithm/services 与生成区域隔离 | 保留实际生成工程、`.ioc` 和工具版本；用户区以工具机制为准 |
| ESP-IDF | 用组件组织职责，区分公开和私有 include/依赖 | 保留 IDF 构建、sdkconfig、芯片与内存/中断限制 |
| Linux 内核/驱动 | 接口、资源所有权、生命周期和验证原则 | Kbuild、子系统目录与原生内核风格，不套应用层 ROS 目录 |
| 已选用 ROS 2 的 Linux/Windows 工程 | 可选采用第 3.3 节包布局、共享接口、节点参数与 launch | 固定发行版/OS/RMW支持组合；核心库与 ROS 包装分开，平台与设备后端分别验证 |
| ROS 1 遗留工程 | 包、msg/srv/action、参数命名空间与核心库解耦 | 保留 catkin、actionlib、参数机制；消息与桥接兼容单独验证 |

STM32CubeMX 的可再生成工程源码不等于普通 build 临时文件；不得机械移入 build 或依赖用户区之外的修改被保留。[ST CubeMX 6.18.1 手册](https://dev.st.com/stm32cube-docs/stm32cubemx/6.18.1/en/docs/markup/CubeMX_UserManual/chapters/04_4_stm32cubemx_user_interface.html)

ESP-IDF 用 `INCLUDE_DIRS/PRIV_INCLUDE_DIRS`、`REQUIRES/PRIV_REQUIRES` 表达边界，使用项目实际 IDF 版本；组件目录与命名不需照搬工作区示意。[ESP-IDF Build System](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/build-system.html)

Linux 内核模块使用 Kbuild，内部头文件可与源码同目录；目标内核树与子系统规则优先于本规范的推荐目录和风格。[Building External Modules](https://docs.kernel.org/kbuild/modules.html)、[Kernel Coding Style](https://docs.kernel.org/process/coding-style.html)

MCU 需要接入 ROS 时，再评估桥接或相应运行方案、可用传输、资源和实时性；共享源代码不等于共享已有二进制、虚拟环境或设备驱动。

### 18.2 DCDC 功能的贯穿示例

以下是后续项目可采用的设计与验收方法，没有绑定具体设备协议，也不是已运行的固件、仿真或实物结论。量程、时限、保护阈值与允许动作需从实际设备资料和项目需求取得。

选择“读取输出状态—在允许条件下提交输出目标—核对实际反馈”这一条链路：

1. **定义合同：** 选择目标控制模式需要的最小能力，声明读状态、请求目标与结果观察的语义；双向运行、其他模式和远程复位等能力仅在真实存在且项目需要时声明。明确单位、方向、当前限制、质量与完成判据。
2. **划清文件：** 公共设备能力接口放在 `include/<project>/devices/`，公共状态类型放在约定的数据接口位置；真实适配在 `src/devices/<vendor>/`，总线与平台后端在 `comm/platform`；仿真实现在测试支持目录。各模块通过公共接口连接。
3. **完成装配：** `bootstrap` 根据目标配置选择真实或仿真实现，创建资源并注入池层；核对必需能力、身份与状态后，按合同决定能否启用控制。
4. **读取状态：** 适配层校验协议并转换工程量，池发布带质量和时间含义的快照；控制只按合同消费可用数据，展示可保留明确标注的最后已知值。
5. **提交目标：** app 提交业务意图，control 核对模式、控制权和联锁，按需调用算法；池关联目标设备和请求，再交由设备适配执行。执行入口核对仍然有效的条件，避免排队期间变化被忽略。
6. **形成反馈：** 按合同区分本地受理、设备响应与实际完成；适配器提供的证据经池关联后交给控制。协议不足以确认完成时，保留未知或未确认状态，不返回假成功。
7. **检验失败路径：** 在仿真中覆盖能力不支持、状态过期、超时后迟到反馈、重连与旧命令、队列满和初始化失败；按声明预算检查其他任务是否被不当阻塞。
8. **检验替换：** 以满足同一合同的另一适配实现运行相同业务场景；上层业务逻辑不因厂商型号分支而改变。真实与仿真可构成一组实现，但对真实实现的结论仅覆盖实际执行的验证环境；若仅有一个实现，不宣称已完成替换验证。
9. **目标验收：** 获取具体设备条件与动作授权后，验证协议、反馈、时序、保护和恢复。仿真通过不能直接升级为真实设备已验收。
