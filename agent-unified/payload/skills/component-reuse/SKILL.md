# 组件提取与跨项目复用

先判断用户要的是只读盘点、组件提取、上游选型还是接入验证。只读盘点输出候选和依据；提取、安装、接入及发布分别遵循当前任务授权，不把找到源码当成安装或生产可用。

## 选择复用对象

- 先找现有公共组件、依赖锁、构建目标和调用方；比较直接使用、局部适配、提取自有代码的成本。相似代码不一定具有相同业务语义。
- 将代码分为纯逻辑、平台适配、项目业务和生成/第三方代码。优先提取已有真实复用需求、边界清楚且能独立验证的部分，不提前建设通用框架。
- C/C++ 分析使用匹配目标的宏、头文件路径及编译数据库；不同芯片、构建选项和内核版本下的依赖不能仅靠文本搜索推断。
- 引用第三方代码时核对仓库、固定提交、根许可证及实际使用文件的声明。仓库内的 vendor、子模块、示例可能采用不同许可证；GitHub 自动识别不是最终许可结论。

## 提取与接入

1. 列出候选的实际依赖：全局状态、硬件寄存器、HAL/RTOS、系统调用、分配器、时钟、日志、编译宏、生成工具和配置。
2. 只为需要替换的依赖提供小接口或适配层。纯协议/算法核心不反向依赖项目业务；硬件驱动自身可依赖目标 HAL，不为统一而隐藏其重要限制。
3. 按 [组件契约](references/component-contract.md) 记录相关接口、所有权、平台和验证约束。小组件可以直接放在已有 README，无需新增完整文档体系。
4. 采用小步迁移：先建立原行为的代表性测试，再移动/解耦，接回原项目。异常行为与历史缺陷应分别标记，不把已知缺陷永久固化为正确契约。
5. 给组件提供独立构建入口和最小调用示例；消费者通过公开接口使用它。只有确有使用场景时才提供多种构建系统或语言绑定。
6. 记录固定版本或 commit、必要补丁及升级方式；各项目独立升级，不能依赖开发者机器上的共享可变目录。

## 嵌入式与跨平台边界

- 明确静态/动态内存、最坏栈占用、可重入性、线程与 ISR 调用限制；单生产者/单消费者条件不等于任意并发安全。
- 时钟单位和回绕、字节序、结构体对齐、整数宽度、DMA 缓冲区寿命及缓存一致性属于适配契约。
- 主机测试、交叉编译、模拟后端和目标板验证分别记录；只在验证过的配置上声明可用。
- Linux 用户态、内核态与 MCU 不能直接互换分配器、锁和 I/O 接口。内核代码应遵循目标子系统接口、许可和版本要求，不照搬用户态库。

## 上游选型

当用户需要现成代码时，按场景查阅 [GitHub 候选索引](references/github-candidates.md)。索引只是查询快照，不是安装清单或安全认证。

可用 `scripts/inspect_github.py --repo owner/name --output metadata.json --date YYYY-MM-DD` 更新公共仓库元数据；有代理时显式提供 `--proxy`。脚本只请求公共 API，不读取令牌、不执行上游源码。它记录默认分支提交和 GitHub 识别的许可证，不能代替文件级审查、版本选择及目标测试。

## 交付证据

说明选择了什么、复用方式、来源与固定版本、改动边界、实际运行的检查、未覆盖的平台/硬件和回退方式。把“已检索”“已审阅”“已构建”“目标验证通过”分开；没有适合的上游时可以明确建议保留自有实现。
