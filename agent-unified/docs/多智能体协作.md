# 多智能体工程协作

查询与采用日期：2026-10-20。

## 方案与范围

采用主智能体统筹、少量子智能体按需并行的方式。用户已要求结合网上方案优化并创建智能体；本次范围为角色配置、协作技能、规则入口、Windows/Linux 安装恢复和相关验证。验收是角色配置有效、安装可预览/幂等/拒绝冲突/回退、已有恢复入口可携带角色；不安装新 Agent 框架，不改模型、权限、MCP 或账号配置，不启动真实设备操作。

主会话承担统筹职责，不再创建一个统筹者来统筹另一个统筹者。八个角色是可选能力，不代表同时运行八个进程：

| 角色 | 用途 | 文件修改 |
|---|---|---|
| `architecture_explorer` | 架构、调用链、模块边界与变更影响 | 只读 |
| `docs_researcher` | 官方资料、API/SDK、手册和标准适用性 | 只读 |
| `software_worker` | 软件模块、脚本、前后端实现 | 仅分配文件 |
| `firmware_worker` | STM32/ESP32、BSP、RTOS、MCU 协议 | 仅分配文件 |
| `linux_worker` | Linux 应用、驱动、内核和设备树 | 仅分配文件 |
| `test_engineer` | 测试设计、回归与指定检查执行 | 仅分配测试文件 |
| `code_reviewer` | 验证后的集中审查与修复增量复核 | 只读 |
| `protocol_safety` | 车载协议、BMS、软硬件接口与安全专项 | 只读 |

模型与推理强度继承父会话，避免跨账号、跨机器使用不可用型号。只读是角色行为约束，不是单独的只读沙箱；权限和 MCP 继承父会话。角色不授予设备动作、发布或其他外部写入权限。

默认启用 1–2 个子智能体，同时最多 3 个且不超过客户端实际额度；小型改动仍由单智能体完成。限制由协作规则表达，保留用户已有客户端配置。若本机明确禁用了 agents，需要先明确调整该设置，不能绕过。

## 协作流程

独立的资料核对、模块实现和测试准备可并行；共享接口先确定、文件单一修改者、最终按集成版本验证。正式流程为：实现及整合 → 编译/基础检查 → 相关功能验证 → 一轮集中审查 → 有问题则修复和增量复核 → 交付。

执行规则只维护在 [多智能体协作技能](../payload/skills/agents-engineering-skill/assets/agents-project-template/skills/multi-agent-coordination/SKILL.md)。它与现有验证技能配合，避免每个角色重复跑整套测试。BMS、真实设备及破坏性测试前的安全审查仍前置。

## 安装与恢复

当前官方方式是在 Codex 用户目录 `agents/` 下放置独立 TOML 文件；工程源码在 `payload/agents/`。每个文件声明角色名、用途和职责，不包含主机绝对路径、密钥、模型覆盖或权限覆盖。

在 `agent-unified` 目录执行（Python 3.11+；Linux 按环境用 `python3`）：

```bash
python install_agents.py
python install_agents.py --apply
# 已审阅本地冲突后才显式替换；事务会保留恢复所需内容
python install_agents.py --apply --replace-existing
# 使用安装命令输出的实际事务目录
python install_agents.py --rollback /path/to/transaction
```

`--codex-home` 可选择目标 Codex 用户目录。默认预览无写入；相同内容无重复写入，冲突在写入前报告。公开技能安装器和完整恢复器也携带角色；已有同名自定义角色需先合并，不静默覆盖。完整恢复显式替换参数为 `--replace-existing-agents`；公开技能安装器沿用 `--replace-existing`。角色安装后，在新的会话核对发现结果；已有会话不保证热加载，新角色文件也不会自动创建运行中的任务。

未安装新客户端或修改账号；不兼容独立角色文件的旧客户端，需要升级到支持该格式的版本，或用已有子智能体工具传递明确职责。不能将“文件存在”报告成“角色已经成功执行”。Linux 使用同一源码，仍需目标客户端验证。

## 使用示例

- “并行完成这个模块：软件智能体修改实现，测试智能体按接口准备测试；合并编译测试通过后交给审查智能体。”
- “先让架构智能体梳理 Linux 用户态与驱动接口，资料智能体核对目标内核文档，再按模块分工。”
- “BMS 保护逻辑先由协议安全智能体核对状态机和阈值来源；固件与测试分别实现，真实充放电不要执行。”

调用角色仍受当前客户端工具接口约束。若当前工具仅接收任务描述而没有角色选择参数，主智能体读取角色文件，将职责作为子任务指令传入，不能杜撰 `agent_type` 等参数。

## 官方依据与取舍

- [OpenAI：Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)：支持独立 TOML 角色、父会话能力继承和按需委派；推荐从独立的读取与分析任务开始，对并发写入保持清晰边界。
- [OpenAI：Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference)：提供 agents 开关、并发和默认模型设置；本方案保留已有设置，角色继承模型。
- [Anthropic：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)：明确子任务目标、工具与输出边界，并按任务复杂度控制投入，减少重复工作。其研究场景的收益不能直接当作本工程的速度承诺。

本次选择原生能力和短角色配置，复用已有领域技能与测试入口；没有必要为相同目标再引入额外运行框架、API 密钥或常驻服务。

## 本机验证记录

2026-10-20，Windows AMD64、Python 3.13.13、Codex CLI 0.163.0-alpha.10.2：基础语法检查通过；角色安装 19 项、恢复 32 项、公开安装器 10 项，共 61 项测试，59 项通过，2 项因 Windows 符号链接权限跳过。规则结构检查无错误或警告。测试只使用临时目录和合成配置；没有执行真实设备或 Linux 实机测试。

8 个角色已通过独立安装器写入本机 Codex 用户目录。当前会话的子智能体工具没有按角色名选择参数，本轮通过委派描述传入角色职责，已实际完成子任务实现与独立审查分工。CLI 的 `debug prompt-input` 可运行，但其输出不包含角色目录，不能据此确认桌面端原生角色发现或热加载。新会话需核对角色选择支持；角色文件安装与角色实际运行分开报告。

独立审查发现的集成入口并发覆盖问题已修复，三个入口共用角色目录冲突保护；新增两项回归测试通过，原审查者增量复核确认修复范围内无新阻断项。
