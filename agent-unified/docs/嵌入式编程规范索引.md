# 嵌入式编程规范：STM32、ESP32 与 Linux 分层索引

查询日期：**2026-10-15**。用途：个人与团队工程选型、编码约定及评审资料入口。本文是来源索引和采用建议，不替代标准正文、芯片手册或项目合规证据。

## 1. 先选适用层，避免规则互相冲突

| 开发对象 | 建议作为基线的资料 | 应补充的内容 |
| --- | --- | --- |
| STM32 Cortex-M 裸机 / RTOS 应用 | BARR-C + CERT C；有安全合规要求时采用合同指定 MISRA 版本 | 对应型号 RM/PM/Errata、CMSIS、Cube HAL/LL 版本、RTOS 端口约束 |
| STM32 BSP / 板级驱动 | ST UM2298、UM2285 + 对应 Cube 包约定 | 初始化/撤销、错误码、总线资源共享、中断与 DMA、静态分析及偏离说明 |
| ESP32 / ESP-IDF 应用与组件 | ESP-IDF Style Guide、API 约定、Error Handling、IDF FreeRTOS 文档 | 实际芯片目标、IDF tag、sdkconfig、内存类型及中断约束 |
| Linux 应用层 | 项目风格 + CERT C；C++ 加 C++ Core Guidelines；接口语义查 POSIX/man-pages | 资源生命周期、线程、信号、短读写、超时、ABI 与目标 libc |
| Linux 内核驱动 | Kernel Coding Style + Driver API + 对应子系统文档 | probe/remove、锁与上下文、MMIO/DMA、设备树、用户态接口、热插拔和电源管理 |
| Linux 内核核心 / 子系统 | Kernel Coding Style、Submitting Patches、Deprecated Interfaces、内存模型和测试文档 | 所在子系统 MAINTAINERS、锁序、RCU、引用计数、UAPI 兼容性 |

**这里的 STM32 MCU 与 STM32MP Linux 是不同层次。** STM32MP 上的用户程序、内核驱动分别按对应 Linux 行执行；不能因为品牌都是 STM32 就套用 Cortex-M 裸机约定。ESP32 家族也包含 Xtensa/RISC-V、单核/多核不同目标，不能统一假设为双核 Xtensa。

风格、安全编码、API 契约、功能安全流程分别解决不同问题。建议共用缺陷预防原则，按目录/构建目标选择风格；不要给全部工程强制同一份 `.clang-format`，也不要把 Linux 内核改造成 MISRA 风格项目。

采用 MISRA 时应建立“版本、适用范围、分析器及配置、人工检查、偏离记录、第三方代码边界”的证据链。一次 Cppcheck 或 clang-tidy 执行不能证明全面合规；也不能把 HAL 的厂商合规声明外推为整机应用合规。

## 3. STM32：官方指南与项目规则怎样结合

| 官方资料 | 应读内容 | 适用边界 |
| --- | --- | --- |
| [UM2298 — STM32Cube BSP drivers development guidelines / ST](https://www.st.com/resource/en/user_manual/um2298-stm32cube-bsp-drivers-development-guidelines-stmicroelectronics.pdf) | BSP 分层、组件/总线接口、目录结构、导出名称及实现示例 | 实际 PDF 首页为 **June 2019，Rev 2，160 页**，不能把搜索引擎抓取日期当修订日期；主要针对 Cube BSP |
| [UM2285 — Development guidelines for STM32Cube Expansion Packages / ST](https://www.st.com/resource/en/user_manual/um2285-development-guidelines-for-stm32cube-expansion-packages-stmicroelectronics.pdf) | 扩展包组织、开发交付、质量要求 | 针对 Cube Expansion Package；质量章节涉及编译、功能测试、静态分析、MISRA 偏离证据，非所有 STM32 应用的统一合同 |
| [STM32Cube HAL qualification / ST](https://www.st.com/resource/en/product_presentation/stm32cube_hal_qualification.pdf) | ST 对 HAL/LL 质量流程、合规报告的说明 | 官方说明 MISRA 版本依系列而异；需要向具体 Cube 包/厂商报告追溯 |
| [CMSIS-Core Cortex-M / Arm](https://arm-software.github.io/CMSIS_6/latest/Core/index.html) | 核心寄存器、异常、中断、启动及内核访问接口 | API/架构资料，不是应用层命名标准；版本须与项目芯片包兼容 |

建议为自己的 STM32 工程落地以下约定（工程建议，不冒充 ST 原文）：

1. 明确 `App / Services / BSP / Drivers / ThirdParty` 的实际依赖方向；按现有工程布局采用，不为了目录名称重构成熟项目。
2. 生成代码、厂商代码和自有逻辑分开维护。生成区域按当前 CubeMX 版本的保留机制修改，保留 `.ioc` 与工具版本。
3. 中断只执行必要且有界的工作；明确 ISR 与任务之间的数据所有权、通知方式及优先级约束。共享变量不靠 `volatile` 代替同步。
4. 对 DMA 缓冲区记录存储区域、对齐、生命周期及缓存一致性策略；Cortex-M7 等带缓存目标按具体 RM/应用笔记验证，不能把所有 STM32 当成一致缓存环境。
5. 所有外设等待要有项目定义的超时与失败恢复；检查 HAL/LL 返回状态，不能把示例中的无限循环直接作为产品错误策略。
6. 对协议字段注明宽度、符号、端序、比例、单位、范围；寄存器访问使用正确宽度与厂商/CMSIS 定义。

尚需具体型号才能补齐的资料：芯片 Reference Manual、Programming Manual、Datasheet、Errata、对应 Cube 固件版本与板卡原理图。不存在一份能替代全部 STM32 型号资料的“编程规范”。

## 4. ESP32：以项目所用 ESP-IDF 版本为准

| 官方资料 / Espressif | 内容 | 使用方式 |
| --- | --- | --- |
| [ESP-IDF Style Guide](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/contribute/style-guide.html) | C/C++/CMake 命名、排版、头文件及文档惯例 | 本次 stable 页面标题为 **v6.1**；实际项目应切换到所用 IDF 版本和芯片目标 |
| [Error Handling](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/error-handling.html) | `esp_err_t`、错误码及可恢复/不可恢复错误处理 | 正常返回成功为 `ESP_OK`；应用应按可恢复性选择返回、清理、重试或终止 |
| [Error Code and Helper Functions](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/system/esp_err.html) | `ESP_RETURN_ON_ERROR` 等错误检查辅助接口 | 检查清理路径及调用上下文，不能机械把所有错误都变成 abort |
| [FreeRTOS (IDF)](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/system/freertos_idf.html) | IDF 调度、多核、任务及临界区行为 | 必须区分原生 FreeRTOS 与 IDF 实现；单核经验不能直接作为 SMP 同步依据 |
| [API Guides](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/) | 内存类型、中断、日志、构建、测试与问题诊断的总入口 | 按正在使用的功能查对应章节，不一次加载全套手册 |

已核对的风格例子：4 空格缩进、不使用 Tab；在不损害可读性的前提下最大行长 120；仅单文件使用的对象/函数用 `static`，公开符号加组件前缀，静态变量按该指南使用 `s_` 前缀。第三方代码保持其上游风格。[来源：ESP-IDF Style Guide](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/contribute/style-guide.html)

建议检查：组件边界、初始化失败回收、任务栈和堆峰值、看门狗策略、ISR 可调用 API、PSRAM/内部 RAM 限制，以及 sdkconfig 与构建产物一致性。只把 `IRAM_ATTR` 写在入口函数上并不能证明整个调用链满足缓存关闭场景；须查所用 IDF 和芯片的内存/中断要求。

## 5. Linux 应用层：没有一套所有应用通用的内核风格要求

| 一手资料 | 解决什么问题 | 注意事项 |
| --- | --- | --- |
| [The Open Group Base Specifications Issue 8 / POSIX.1-2024](https://pubs.opengroup.org/onlinepubs/9799919799/) | 系统接口的标准语义和可移植边界 | 官方[下载说明](https://pubs.opengroup.org/onlinepubs/9799919799/download/index.html)核实 Issue 8 / IEEE 1003.1-2024。不是编码排版规范 |
| [Linux man-pages / 项目维护者](https://man7.org/linux/man-pages/) | Linux 系统调用、libc API、Linux 扩展行为 | 与目标内核、glibc/musl 版本共同核对；不能假定新版文档描述的接口旧 BSP 均支持 |
| [pthreads(7)](https://man7.org/linux/man-pages/man7/pthreads.7.html) | POSIX 线程接口与实现差异 | 注意返回错误码和设置 errno 的 API 并不相同 |
| [signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html) | 异步信号处理器中可安全调用的接口 | 普通线程安全不等于异步信号安全 |
| CERT C / C++ Core Guidelines | 安全编码、所有权、资源释放、接口和并发设计 | 见通用资料表；风格仍遵循所维护项目 |

推荐项目门禁：检查文件描述符/锁/内存所有权，正确处理短读写、`EINTR`、`EAGAIN`、超时、关闭和取消；把用户输入与日志脱敏作为边界检查。C++ 用 RAII 表达资源生命周期；能在宿主运行的纯逻辑测试可使用 Sanitizer，目标 ARM/Linux 的 ABI、设备权限及实际 I/O 仍需目标端验证。

不要统一自动重试所有系统调用：按该调用的语义决定；重试是否幂等、已经完成多少字节、是否可能产生重复外部动作都需要明确。

## 6. Linux 驱动层：内核规则加硬件生命周期

| 官方内核文档 | 重点 |
| --- | --- |
| [Linux Kernel Coding Style](https://docs.kernel.org/process/coding-style.html) | 驱动和内核共用的 C 风格基础 |
| [Driver Model](https://docs.kernel.org/driver-api/driver-model/index.html) | device/driver/bus 对象、绑定与生命周期 |
| [Devres — Managed Device Resource](https://docs.kernel.org/driver-api/driver-model/devres.html) | `devm_*` 管理资源的释放时机；托管资源不等于自动解决并发与硬件停机顺序 |
| [Dynamic DMA Mapping Guide](https://www.kernel.org/doc/html/latest/core-api/dma-api-howto.html) | DMA 地址、映射、方向、同步与一致性 |
| [ioctl based interfaces](https://docs.kernel.org/driver-api/ioctl.html) | 命令定义、用户态 ABI、固定宽度类型、32/64 位兼容和信息泄漏 |
| [Writing Devicetree Bindings in json-schema](https://docs.kernel.org/devicetree/bindings/writing-schema.html) | YAML binding、属性约束与 schema 验证 |
| [Lock types and their rules](https://docs.kernel.org/locking/locktypes.html) | 锁类型、允许的上下文与 PREEMPT_RT 差异 |

评审建议：先标出每个入口运行在进程、线程化中断、硬中断或其他原子上下文；再检查是否允许睡眠以及分配标志。确认 MMIO 使用正确 accessor、用户指针经适当接口访问、返回错误语义稳定、probe 失败能完整释放。remove/断电前需要停止硬件、同步中断/工作队列/定时器并处理仍在使用的对象，不能仅依赖 `devm_*` 自动释放。

驱动属于内核一部分，但不是所有内核问题都是驱动问题；块、网络、TTY、IIO、GPIO 等子系统还有各自契约，按所用接口继续读取子系统文档。厂商 5.10/6.1 等 BSP 应优先看其源码树中的 Documentation 和实际补丁，不能照搬 latest API。

## 8. 适合现有工具箱的落地顺序

1. **项目声明**：记录芯片/板卡、SDK/内核 tag、语言标准、交叉编译器、RTOS/配置以及采用的标准版本。规则进入项目目录，不把所有平台条文塞进全局 AGENTS。
2. **格式检查**：每个领域单独选择 `.editorconfig` / `.clang-format`；ESP-IDF 和内核优先复用所在源码版本的配置。
3. **静态分析**：已有 Cppcheck、clang-tidy 可复用，但必须先核实交叉编译宏、头文件、目标 CPU 和 `compile_commands.json`；不能拿宿主默认编译参数推断固件正确性。
4. **聚焦测试**：用户态做单元/协议/错误路径测试；MCU 加栈/时序/故障恢复与目标板测试；驱动/内核加子系统测试、锁检查、KUnit/kselftest 等适用检查。
5. **合规证据**：若合同要求 MISRA 等，建立单独的合规矩阵、人工规则检查与偏离审批；工具覆盖范围、误报处置和第三方代码边界明确记录。

下列仅为目标 Linux 源码树内的参考命令，**本次未在实际内核/驱动工程运行**：

```sh
# 补丁风格检查
./scripts/checkpatch.pl --strict change.patch

# 外置模块构建 / Sparse；KDIR、PWD、ARCH、CROSS_COMPILE 由项目提供
make -C "$KDIR" M="$PWD" W=1 modules
make -C "$KDIR" M="$PWD" C=1 CHECK=sparse modules

# 在相应内核源码树检查 Devicetree schema 与编译出的设备树
make dt_binding_check
make dtbs_check
```

真实硬件、Linux 构建环境、Sparse、dt-schema 及项目编译链是否可用应分别检查。本次任务完成的是规范查找与工具环境维护，没有编译 STM32/ESP32 固件、加载内核模块或操作真实设备。

## 9. 来源与访问说明
